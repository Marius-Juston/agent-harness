# Research: free secret, dependency and code scanning for private repositories

Status: v1 (2026-10-12). Issue: #15 (and the generic part of a consuming project's security pipeline request).
Labels: SOURCED = cited and fetched; VERIFIED = measured in this repo (script named); BELIEVED = judgment; ASSUMED = unchecked premise.
Search coverage: tool documentation only (no literature search: the question is which maintained tools fit); `uv run dev lit status` on 2026-10-12 showed openalex, crossref, europepmc and arxiv up, s2 down (HTTP 429).
Companions: [agent-harness.md](agent-harness.md) (why checks are enforced, not described).

## 0. Findings in one paragraph
GitHub runs secret scanning for free on public repositories only, so a private user-owned project needs its own. The harness uses four free tools, each run where it fits. **gitleaks** (MIT) runs as a pre-commit hook on staged changes and over the whole history in the CI `check` job. **`uv audit`** checks uv.lock against OSV and needs no extra dependency. **`uv export --format cyclonedx1.5`** writes an SBOM that is kept with each CI run. **ruff's S rules** (the bandit port) run in the gate. The audit and the history scan need the network, so CI runs them rather than `dev check`. All four fail on fixtures: `uv run pytest -m live tests/test_security.py` checks this, and CI runs it as a step of this repository's `check` job.

## 1. Question and scope
Which free tools stand in for GitHub secret scanning, dependency alerts and code scanning on a private repository, and where should each one run (pre-commit, `dev check`, CI)? Semgrep CE (the static-analysis half of that request) is not covered. ruff S covers Python, and a second static analyzer is a follow-up.

## 2. Findings
- Secret scanning runs automatically for free only on public repositories, and user-owned private repositories are not listed as covered without paid Secret Protection, per [GitHub's secret scanning overview](https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning) (SOURCED).
- gitleaks is MIT-licensed, its latest release is v8.30.1 (2026-03-21) and its last push was 2026-09-30, not archived (VERIFIED, `gh api repos/gitleaks/gitleaks` and `.../releases/latest`, 2026-10-12). It ships a pre-commit hook, a `git` command that scans patches through `git log -p`, a `dir` command, `--redact`, and a `.gitleaksignore` file of fingerprints for false positives, per [the gitleaks README](https://github.com/gitleaks/gitleaks) (SOURCED).
- The gitleaks hook builds from Go source (`language: golang`). prek installs managed toolchains, Go among them, when a hook needs one, per [the prek home page](https://prek.j178.dev/) (SOURCED). No Go was installed here, and `uvx prek run gitleaks` still built and ran the hook in about 27 s on the first run (VERIFIED, `time uvx prek run` in a scratch fixture repo with a staged file, 2026-10-12; the live tests in `tests/test_security.py` repeat the run). There is no PyPI wheel to pin through uv.lock (VERIFIED, `curl -s https://pypi.org/pypi/gitleaks/json` answers with no `info`, 2026-10-12), so the pin is the hook's `rev`.
- Overriding the hook's `entry` under an `alias` with `stages: [manual]` gives a whole-history scan that CI runs as `prek run -c .pre-commit-config.yaml --hook-stage manual gitleaks-history --all-files` (`-c` keeps prek to the root config; without it, prek's workspace mode also ran the copy in `template/` and scanned twice). A fake GitHub token found this way fails, and so does a token committed and then deleted (VERIFIED, `test_ci_step_fails_on_a_committed_fake_secret`). The token is generated from a fixed seed at run time because a literal token in a test would trip the scan of this repository.
- `uv audit` checks every group and extra of the project against OSV (`https://api.osv.dev/`), also reports adverse statuses such as deprecation and quarantine, needs the network, and accepts `--ignore <id>` and `--ignore-until-fixed <id>`, per [the uv CLI reference](https://docs.astral.sh/uv/reference/cli/) (SOURCED). uv 0.12.23 marks it experimental, which is why the workflow passes `--preview-features audit-command`. A fixture pinned to `requests==2.19.0` exits 1, and this repository's lock exits 0 (VERIFIED, `test_ci_audit_fails_on_a_pinned_vulnerable_dependency`).
- pip-audit (Apache-2.0) is the alternative. Its default service is PyPI and OSV is an option, `--disable-pip` needs hashed requirements, and its project mode reads `pyproject.toml` and `pylock.*.toml` but not uv.lock, per [the pip-audit README](https://github.com/pypa/pip-audit) (SOURCED). That means an export step, and git-sourced packages without hashes (the harness itself, in a consumer) would need special handling, so it was not chosen (BELIEVED).
- `uv export --format cyclonedx1.5` writes a JSON CycloneDX 1.5 document of the project and every dependency. The format is in preview, per [uv's export guide](https://docs.astral.sh/uv/concepts/projects/export/) (SOURCED). The harness lock exports 32 components (VERIFIED, `uv export --frozen --format cyclonedx1.5 --output-file sbom.json` then `len(json.load(...)['components'])`, 2026-10-12). Without `--quiet` the export also prints the document to stdout, so CI passes `--quiet`.
- Ruff's S603 rule fires on every subprocess call and "is prone to false positives as it is difficult to determine whether the passed arguments have been validated", per [the S603 page](https://docs.astral.sh/ruff/rules/subprocess-without-shell-equals-true/) (SOURCED). devkit exists to run git, gh, uv and tools with argument lists (26 S603 and 22 S607 findings, every one such a call), so this repository ignores S603 and S607 repo-wide. The template keeps both, because a consumer's subprocess calls are rarer and worth a justified `noqa` (BELIEVED).
- Expat versions before 2.7.2 may be open to billion laughs, quadratic blowup and large-token attacks, per [Python's XML security notes](https://docs.python.org/3/library/xml.html#xml-vulnerabilities) (SOURCED). This interpreter (CPython 3.13.11) links expat 2.6.3 (VERIFIED, `uv run python -c "import pyexpat; print(pyexpat.EXPAT_VERSION)"`, 2026-10-12). devkit therefore refuses network XML that has a DTD or an entity declaration (`devkit/netsafe.py`) instead of adding defusedxml. The Atom feeds it reads never carry one, and without one there is nothing to expand (BELIEVED).

## 3. Recommendation for this project
Adopted: a gitleaks hook in both pre-commit configs, security steps in the `check` CI job of this repository and of the template, so a PR bills one runner (#57) (history scan, `uv audit`, an SBOM uploaded as the `sbom` artifact; each step runs even when an earlier one failed). They also run weekly on a schedule, because new advisories appear against an unchanged lock. The audit uses `--locked`, so a stale lock fails instead of being audited as it is. setup-uv pins uv in that job because both features are in preview. The template exempts `docs/research/_scratch/**` (throwaway probe scripts) from all S rules, and ruff `S` in both pyprojects with tests allowed `assert`. Handle a false positive with a fingerprint in `.gitleaksignore`, or `--ignore <id>` on the audit with the reason beside it, never by removing the step.
