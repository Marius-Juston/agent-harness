## 0. Findings in one paragraph
In repo-E's first harness week (2026-10-11..16: 16 lead sessions, 644 subagents, 188 merged PRs, every agent on Opus 5.5) the harness cost **$2,756-2,928 API-equivalent, about $15 per merged PR**, and the cost is context size times turns: cache reads 48 %, cache writes 29 %, output 20 %, uncached input 3 %. Corrected for the transcripts' 6.4x output undercount, **researchers are 50 % of spend, builders 23 %, the lead 16 %**, and the three review roles 8 %. So the money is in the research loop, the lead's 372k-token average context, and fixed tool schemas (the unused Artifact schema alone is 46 % of a builder's first call), not in harness prose (all of HARNESS.md plus CLAUDE.md is under 1 %). The review loop already converges per role about as well as Anthropic's after their fix (80 % of series pass after one review-and-fix round), but security review of hand-written filters does not (66 %), and **43 % of failing later rounds are bugs the previous fix introduced, 25 % missed instances of a class already flagged**; extra rounds caught none of the 6-9 % of reviewed PRs that later needed a fix. For Opus 5.5 the per-role lever is **effort, not model or prose**: thinking is always on, Sonnet 5.5 is exactly half price on every token kind (cache reads $0.10, settled from the pricing page) but buys nothing on code that Opus at `low` does not, and cheaper reviewers on safety gates are a bad trade for about 3.5 % of spend. The ranked changes (§9): withhold unused tool schemas (about 3-5 % of spend), a runnable probe per blocking bug class, lead compaction near 300k (about 5-6 % of spend), explicit effort per agent with gate-driven escalation, and a review verdict contract that never merges an open blocker; each ships with a pre-registered measure on cost per merged issue (cache writes priced apart), review rounds per role and post-merge defect rate, which `dev agent-stats` cannot compute yet (#255). Do not add brevity rules, cap review rounds into a merge, compact `dev check` output, move reviewers to Sonnet, or read this one window as causal (§8).

## 1. Question, scope and data
The question ([QUESTION.md](_scratch/harness-efficiency/QUESTION.md)): which changes to agent-harness raise the effectiveness of a harness-run repository (merged, correct work per owner-hour; fewer review rounds and reworks), and which cut tokens at equal effectiveness? The owner asked specifically how Opus 5.5 should be handled per role.

**repo-E** is the private product repository that consumes this harness (the code name used in [fix-now-vs-defer.md](fix-now-vs-defer.md)); PR and issue numbers in §4 refer to it, and its security findings are counted, not described, because this repository is public.

Evidence, in two rounds (gaps: [r1](_scratch/harness-efficiency/gaps-r1.md), [r2](_scratch/harness-efficiency/gaps-r2.md)):
- **Transcripts.** repo-E's Claude Code transcripts for 2026-10-11..16 and the client cost records (`cost-state`), read by the scripts in the round folder ([r1-usage-logs](_scratch/harness-efficiency/r1-usage-logs.md), [r2-research-and-lead-cost](_scratch/harness-efficiency/r2-research-and-lead-cost.md), [r2-surface-audit](_scratch/harness-efficiency/r2-surface-audit.md), [r2-review-convergence](_scratch/harness-efficiency/r2-review-convergence.md), [r2-against](_scratch/harness-efficiency/r2-against.md)). Harness plugin v0.1.4-v0.1.7; the text audited is v0.1.9.
- **Anthropic.** All claude.dev blog posts ([r1 A](_scratch/harness-efficiency/r1-blog-review-automations-cloud-mods.md), [B](_scratch/harness-efficiency/r1-blog-sonnet-evals-cost-effort.md), [C](_scratch/harness-efficiency/r1-blog-speed-opus55-context-skills.md), [D](_scratch/harness-efficiency/r1-blog-workflows-html-caching-seeing.md)), the 26 anthropic.com/engineering posts and the Claude Code docs ([r1-engineering](_scratch/harness-efficiency/r1-engineering-and-docs.md)), and the platform docs on effort, models and prompting ([r2-opus55-handling](_scratch/harness-efficiency/r2-opus55-handling.md)).

Limits that apply to everything below. One six-day window, four harness versions, one repository's task mix, one model; run-to-run token use varies up to 30x on the same task (Bai et al. 2026 ([arXiv 2604.22750](https://arxiv.org/abs/2604.22750)), SOURCED abstract). The window ranks hypotheses; it does not prove any change works (§8). ## 2. Where the spend goes, corrected for the output undercount
- **Totals.** The client cost records (`cost-state`) hold a running total per Claude Code process, and a resumed session starts a new process from 0. Summed per process they give **$2,756**; the round-1 figure of $2,231 kept only each session's last record and lost a $525 process. One session's records also cover only $7.7 of about $128 of transcript-priced cost, so the window estimate is **about $2,928** (transcript-priced cost plus the hidden output measured in the sessions the records cover). That is **$14.7-15.6 per merged PR**, an upper bound per PR: the 188 count is repo-E's merged PRs and leaves out the agent-harness PRs worked from the same sessions; it includes research PRs (VERIFIED, [cost_segments.py](_scratch/harness-efficiency/scripts/cost_segments.py), [synthesis_checks.py](_scratch/harness-efficiency/scripts/synthesis_checks.py) §0; [transcript_stats.py](_scratch/harness-efficiency/transcript_stats.py) now sums per process too). Fitted prices per M tokens match Opus 5.5 list prices with 1-hour cache writes: input 4.09, output 20.05, cache read 0.20, cache write 7.95 (VERIFIED, same script; list prices SOURCED, [Pricing](https://platform.claude.com/docs/en/about-claude/pricing), fetched 2026-10-19).
- **By token kind.** Cache read 47.9 %, cache write 29.4 %, output 19.7 %, uncached input 2.5 %, Haiku 5.5 side calls 0.4 %, other models 0.2 % (VERIFIED, [cost_segments.py](_scratch/harness-efficiency/scripts/cost_segments.py): token counts of the per-process cost records, each model at its own list prices, Haiku at its up-to-100k prompt prices (ASSUMED for its short side calls)). Cost is context x turns plus content written once; output (including hidden thinking) is a fifth.
- **The undercount.** Transcript `usage` records 4.2 M output tokens against 27.0 M Opus 5.5 output tokens in the per-process cost records (6.4x): output is logged at stream start (VERIFIED, [r2_cost_phases.py](_scratch/harness-efficiency/r2_cost_phases.py); 886 of 7,089 sampled long messages logged under 100 output tokens, [r2-against](_scratch/harness-efficiency/r2-against.md) §6). The round-1 per-agent table priced transcript tokens and so understated output-heavy roles. Corrected model: a turn's output is its visible characters x 0.443 tokens/char (least-squares fit of cache growth over 30,818 turns, R² 0.56) plus the billed remainder spread evenly, 233 tokens per turn (the even spread is ASSUMED). The model has no uncached input (absent from transcripts) and totals $2,356, 85 % of the $2,756 in the records; the role shares barely moved from the earlier fit (VERIFIED, rerun 2026-10-19 after the per-process fix).

- **Tool-result clearing would cost more.** A 1-hour cache write is about 40x a read, and clearing invalidates the cached prefix (SOURCED, [context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)); naive clearing policies added 4-11 % to researcher cost and an oracle saved at most 2-4 %. Claude Code does not send it anyway (VERIFIED, all 17,239 logged requests).

## 3. Handling Opus 5.5, role by role
**What the platform allows (SOURCED).** Opus 5.5 thinking is always on (adaptive); `thinking: disabled` returns 400, and effort is "the primary control for how much the model reasons and what a request costs" with default `medium` ([Effort](https://platform.claude.com/docs/en/build-with-claude/effort)). In Claude Code thinking cannot be turned off, `MAX_THINKING_TOKENS=0` has no effect, "think hard" is ordinary text, and there is no per-subagent thinking setting ([Model configuration](https://code.claude.com/docs/en/model-config)). Subagent effort resolves per-invocation `effort` parameter > frontmatter `effort` > session level, and `CLAUDE_CODE_EFFORT_LEVEL` beats all of them ([Create custom subagents](https://code.claude.com/docs/en/sub-agents)). So the only per-role levers are `model` and `effort`.

**What happened (VERIFIED, `api-request` records, [r2_cost_phases.py](_scratch/harness-efficiency/r2_cost_phases.py)).** Researcher and research-auditor ran at `high` (their frontmatter); builder, tester, reviewer, security-reviewer and the lead ran at `medium`, inherited from the owner's session. One `/effort` in the lead would have moved every worker. No subagent made an Agent call (0 in 655 runs, [r2-opus55-handling](_scratch/harness-efficiency/r2-opus55-handling.md) §1.4), so worker self-delegation, which Anthropic warns Opus models over-use, is not happening here.

**Evidence for the settings** (Anthropic measurements: vendor benchmarks, 2-3 pooled runs, not re-measured here; labelled per bullet).
- SOURCED. Effort curve, Opus 5.5 on a SWE-bench Pro subset: `low` 87.4 % solved, `medium` 92.8 %, `high` 95.3 % at $0.29 per task, `xhigh` 96.7 % (one run). "`medium`, failures re-run at `high`" reached about 97 % at about $0.24 and "`low`, failures re-run at `high`" about 97 % at $0.17, with the condition "you need a failure signal … a checker that passes bad work lets those failures through" ([Optimizing for cost and intelligence](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence), re-fetched 2026-10-19).
- SOURCED. Model: "Each of Claude Opus 5.5's token prices, cache reads included, is twice Claude Sonnet 5.5's, but on the SWE-bench Pro subset Opus 5.5 at `low` solved about the same share of tasks as Sonnet 5.5 at its default" ([same page](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)). Writing code on Sonnet buys nothing Opus at `low` does not.
- SOURCED. Research is effort-sensitive: Opus 5.5 at `low` scored 13.3 points below `medium` on DRACO, 3.4 on HLE and 14.0 on a physics set ([same page](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)); `medium` against `high` for research is unmeasured.
- SOURCED. Edge cases: on Terminal-Bench 3.0 (numbers from the post's figure description), Opus 5.5 went from 36.6 % at `low` to 65.7 % at `max`, and "Opus 5.5 at high matches Fable 5.1 at max (58.9% against 58.0%) on half the tokens"; "higher effort is best for tasks with lots of hidden edge cases", and effort "does not fix when the model has the wrong approach" ([Spending your effort](https://claude.dev/blog/spending-your-effort/), claude.dev).
- SOURCED. Moving down: "Move down to Sonnet or Haiku for lookups, not for writing code"; "Keep judgment calls on the main model"; high effort "pays for itself on a task where it saves one retry" ([What a task costs on Opus 5.5](https://claude.dev/blog/what-a-task-costs-on-opus-5-5/), claude.dev).
- SOURCED. Prompt style: drop "think carefully" lines; name the stops you want ("Stop and ask only when you can't continue without me, or before anything destructive") ([Getting the most out of Opus 5.5](https://claude.dev/blog/getting-the-most-out-of-opus-5-5/), claude.dev). Verification rituals and self-delegated double-checks waste tokens; an independent reviewer of another agent's diff is the endorsed writer-verifier pattern ([r2-opus55-handling](_scratch/harness-efficiency/r2-opus55-handling.md) §1.4, from the Opus 5 prompting guide and [Claude Code best practices](https://code.claude.com/docs/en/best-practices)). The harness text already has no "think" or "double-check" prose (VERIFIED, grep, same file A10).

## 4. The review loop
Data: 188 merged repo-E PRs and 73 agent-harness PRs since 2026-10-11, 213 review-agent transcripts; a round is one review pass ending in a hand-back; a series is one role's rounds on one PR (VERIFIED, [review_convergence.py](_scratch/harness-efficiency/review_convergence.py); categories hand-coded by one coder, no second rater).
- **Convergence is good per role, except security of hand-written filters.** Round 1 estimated "mean 2.43 rounds, 20 % one-round passes"; that summed code, security and audit comments on one PR and counted confirmations. Per role, 135 of 169 series pass after one review-and-fix round (80 %, 95 % CI 73-85 %): code 91 %, audit 87 %, security 66 % (CI 54-76 %); mean rounds to a pass verdict 1.81. Seven series (4 %) took 5 or more rounds, all security, all deny-list or parser gates (VERIFIED). Anthropic reports 65 % → 78 % one-round passes, 8.9 % → 1.5 % needing five or more, mean 2.08 → 1.32 (SOURCED, [How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/), figure caption; no N or interval; their definitions differ, so the comparison is indicative).
- **Later rounds mostly confirm; when they block, the previous fix is usually the cause.** 64 % of the 151 later rounds found nothing blocking. Of 51 failing later rounds: introduced by the previous fix push 22 (43 %, CI 31-57 %), another instance of an already flagged class 13 (25 %, CI 16-39 %), missed earlier and unrelated 6, minor residue 8, new input 2, **pre-existing on main 0** (CI 0-7 %) (VERIFIED). Anthropic's "about 59%" of repeat flags on old code (SOURCED, [same post](https://claude.dev/blog/solving-code-review-at-anthropic/)) does not carry over: here the problem is fix churn and class coverage, not old code.
- **What blocks.** Of 60 sampled round-1 findings, 45 % are substantive, 37 % minor, 8 % PR-body or process, 7 % follow-up scope, 3 % pre-existing, and **0 % something `dev check` already enforces** (VERIFIED). The share of non-functional findings matches the field: 75 % of 759 defects found in nine industrial and 23 student reviews did not affect visible functionality (SOURCED, Mäntylä & Lassenius 2008 ([doi 10.1109/tse.2008.71](https://doi.org/10.1109/tse.2008.71)), abstract).
- **What it costs.** Reviews $167 (round 1 mean $0.72, later $0.36); the fix resumes they trigger $281 (builders $1.27, researchers $1.70 each); lead calls $49 at least: about $497, 17-18 % of the corrected total (a lower bound). For comparison, the iterative code-review stage took 59.4 % of tokens in ChatDev runs of 30 tasks on GPT-5 (SOURCED, Salim et al. 2026 ([arXiv 2601.14470](https://arxiv.org/abs/2601.14470)), abstract; a different system and model). One extra review-and-fix round costs about $1.89, a confirmation-only round about $0.55 (VERIFIED; rerun 2026-10-19 with transcripts restricted to the window, which reproduces $167, $281 and $49; output priced from visible text, so lower bounds). Anthropic names the mechanism: "noise costs more when the author is an agent", which fixes every nit, "which means another commit and another round of review" (SOURCED, [same post](https://claude.dev/blog/solving-code-review-at-anthropic/)).
- **Escapes.** No reverts on main. A blame of each `type:bug` fix traced 9 of 141 reviewed PRs (6 %, CI 3-12 %) to a defect filed after merge, 13 (9 %) counting UI and model-wrapper candidates; a lower bound, 3-8 days of follow-up. Live smoke runs, property tests, evals and later use found them; **no later review round found one**, and the three longest security series still leaked same-class bugs (VERIFIED; SZZ-style tracing over-blames, so each pair was checked against the issue text, as Rosa et al. 2021 ([doi 10.1109/icse43902.2021.00049](https://doi.org/10.1109/icse43902.2021.00049)) motivate).
- **Field evidence on review and defects is mixed.** Review coverage and participation predicted post-release defects in Qt, VTK and ITK (up to 2 and 5 extra defects per component when low; SOURCED, McIntosh et al. 2014 ([doi 10.1145/2597073.2597076](https://doi.org/10.1145/2597073.2597076)), abstract), but a replication on Qt and Chrome found the effect unstable and models without review measures fit as well or better (SOURCED, Krutauz et al. 2020 ([arXiv 2005.09217](https://arxiv.org/abs/2005.09217)), abstract). LLM review alone is weak: PRs reviewed only by a code-review agent merged at 45.2 % against 68.37 % for human-only review (SOURCED, Chowdhury et al. 2026 ([arXiv 2604.03196](https://arxiv.org/abs/2604.03196)), abstract, 3,109 PRs); in industry 73.8 % of automated comments were resolved but PR closure time rose from 5 h 52 min to 8 h 20 min (SOURCED, Cihan et al. ([arXiv 2412.18531](https://arxiv.org/abs/2412.18531)), abstract). Different models catch different errors: in injected-error paper review the best configuration caught 71.6 % and the union of six models 83.3 % (SOURCED, Nguyen et al. 2026 ([arXiv 2606.19749](https://arxiv.org/abs/2606.19749)), abstract; paper review, not code).
- **Self-preference argues for more reasoning, not a cheaper reviewer.** Harmful self-preference persists where the evaluator errs as a generator, and a long chain of thought before the verdict reduces it (SOURCED, Chen et al. 2025 ([arXiv 2504.03846](https://arxiv.org/abs/2504.03846)), abstract). That supports a reviewer of another family or at higher effort, not a lower tier of the same family (BELIEVED, [r2-against](_scratch/harness-efficiency/r2-against.md) §1).

So the levers are, in order: catch a whole bug class with a runnable probe and rerun every earlier probe after each fix (targets 69 % of failing later rounds and the same-class escapes); tag findings so non-blocking ones stop costing fix resumes and confirmation rounds; and escalate the approach after round 3 instead of reviewing again (BELIEVED; changes #2 and #5 in §9).

## 5. Fixed context, tool output and workflow friction
- **Prescribed commands the platform refuses.** 139 of 141 builder runs and all 10 tester runs hit at least one worktree-isolation refusal, 685 in all. The plain `uv run dev pr <n> --summary - <<'EOF'` form passed 102 of 105 times; with a trailing `2>&1 | tail` it was refused 105 of 106 times; the lead skill's cross-repo `cd <abs> && …` form caused 146 refusals (VERIFIED, [surface_probes.py](_scratch/harness-efficiency/scripts/surface_probes.py)). Claude Code refuses "when it can't verify from the command text that any git the command runs stays inside the worktree" (SOURCED, [worktrees](https://code.claude.com/docs/en/worktrees)). Agents pipe `dev` output (785 times by builders) because it is long, which turns the prescribed form into a refused one (VERIFIED).
- **Tool output.** `dev check` output is already a summary: all of it in the window is worth about $2, `cite-check` about $2, all `dev lit` output about $37, and one extra researcher turn erases a 1,000-token cut (VERIFIED, [power_and_savings.py](_scratch/harness-efficiency/scripts/power_and_savings.py)). Cutting tool output can raise cost: a 38.4 % cut in delivered tool-output tokens raised billed cost 6.8 % in Claude Code, token reduction correlated weakly with cost reduction (r = 0.15), and compression changed trajectories (SOURCED, Weinberger & Hozez 2026 ([arXiv 2607.12161](https://arxiv.org/abs/2607.12161)), abstract; per r2-against's full-text read, success did not fall and the effect came from extra turns). Trajectory reduction without loss exists (input −39.9-59.7 %, cost −21.1-35.9 %; SOURCED, Xiao et al. 2025 ([arXiv 2509.23586](https://arxiv.org/abs/2509.23586)), abstract), but it edits history, which Claude Code owns.
- **Read habits.** Agents read with `grep`, `sed -n` and `cat` (28,911 Bash calls against 1,301 Read), steered by Claude Code's own auto-mode reminder, and `dev code` is 3-6 % of navigation whether or not HARNESS.md is loaded (VERIFIED, natural experiment across the two repositories, [surface_audit_extra.py](_scratch/harness-efficiency/scripts/surface_audit_extra.py)). Whole-file dumps past the read guard are rare (3 cases). The side effect is "File has not been read yet" on 5.8 % of builder edits (VERIFIED).
- **Skills rarely load.** The Skill tool was called 16 times in 16 lead sessions (VERIFIED, [transcript_stats.py](_scratch/harness-efficiency/transcript_stats.py)); in Vercel's evals a skill was never invoked in 56 % of cases and an inline docs index scored 100 % against 53-79 % for skills (SOURCED, [Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals); no task count or model given).

## 6. Instruction text
- **Text is cheap; conflicts and dead rules are the cost.** HARNESS.md plus CLAUDE.md is about 1.4k tokens, $10-18 per window (VERIFIED, §2). Anthropic "removed over 80% of Claude Code's system prompt for models like Claude Opus 5 and Claude Fable 5 with no measurable loss" and found that conflicting messages make Claude "think more carefully about these overlapping and conflicting messages before deciding what to do" (SOURCED, [The new rules of context engineering](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/), claude.dev). Here the hand-back limit is stated as 25, 20 and 30 lines in different files, and "run `dev check` once at the end" is broken by 98 % of builder runs because the completion gate needs a pass on HEAD (VERIFIED, [r2-surface-audit](_scratch/harness-efficiency/r2-surface-audit.md) F4, F5).
- **Hook-enforced prose does no work.** pip, `.env`, generated-file and push-to-main rules appear in HARNESS.md, builder.md and reviewer.md, were still attempted (6 pip, 13 `.env`), and the hooks blocked them with the fix in the message (VERIFIED, same file F7). "Batch independent reads" and "navigate by symbol" showed no lift where HARNESS.md was loaded (same file F2, F6).
- **One prose rule did work.** "Never curl the literature APIs" moved direct calls from 33 % of researcher runs to 1 of 23 after it arrived (small sample); a hook (#227) makes it hold without the prose (VERIFIED, same file F8).
- **Brevity rules are dangerous and our evals cannot see the damage.** Anthropic shipped "keep text between tool calls to ≤25 words. Keep final responses to ≤100 words" after weeks of evals, then, in broader line-by-line ablations, one evaluation showed "a 3% drop for both Opus 4.6 and 4.7" and they reverted it (SOURCED, [An update on recent Claude Code quality reports](https://www.anthropic.com/engineering/april-23-postmortem), anthropic.com). At a 70 % base pass rate, detecting a 3-point drop needs 3,763 trials per arm; 30 trials per arm detect only a 35-point drop (VERIFIED, [synthesis_checks.py](_scratch/harness-efficiency/scripts/synthesis_checks.py) §6). Context files raise cost over 20 % without raising success, yet their instructions "are well followed" and are "useful for specifying non-standard coding practices" (SOURCED, Gloaguen et al. 2026 ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)), abstract), which is what HARNESS.md mostly is.
- So cut only what is duplicated, conflicting or enforced by a hook, with hook-denial counts as the guardrail, and never cut on word count alone (BELIEVED; change #12).

## 7. Contradictions between the round files
Resolved by the stronger evidence:
1. **Sonnet 5.5 cache-read price.** The pricing page lists Opus 5.5 cache hits at $0.20 and Sonnet 5.5 at **$0.10 per M tokens**, "0.05x the base input price" for both (SOURCED, [Pricing](https://platform.claude.com/docs/en/about-claude/pricing), fetched 2026-10-19), and the optimizing page says each Opus 5.5 price, "cache reads included, is twice Claude Sonnet 5.5's". The Sonnet 5.5 launch post's table lists $0.20 for both ([Building with Claude Sonnet 5.5](https://claude.dev/blog/building-with-claude-sonnet-5-5/), 2026-09-28, re-fetched). The pricing page is the current primary source and wins. Consequence: Sonnet costs **exactly 0.50x Opus for any token mix** and breaks even at 2.0x the tokens; moving the three review roles would save $100 (4.2 % of modelled spend, $0.53 per merged PR), security-reviewer and research-auditor alone $82 (3.5 %), not r2-against's $55, and the researcher role $589 (25 %), not r2's 28 % (VERIFIED, [synthesis_checks.py](_scratch/harness-efficiency/scripts/synthesis_checks.py) §1, §3). The verdicts in §3 do not change: the review saving is still small against an asymmetric loss.
2. **Hand-back caps 25 / 20 / 30.** One number, 25 lines, stated once in each agent body (the plugin travels without HARNESS.md); drop the HARNESS.md copy (BELIEVED; #263).
3. **Cache TTL.** Round 1 said only builder, researcher and tester set a 1-hour TTL; the project setting overrides frontmatter and 99.6 % of writes were 1-hour (VERIFIED, §2). Keep it.
4. **Review baseline.** "Mean 2.43 rounds" counted roles together; the per-role figures in §4 replace it (VERIFIED).
5. **Security-reviewer effort.** r2-opus55 recommends `high`; r2-against rejects lowering it and asks for the same recall eval before raising it. Both hold: raise it behind the planted-defect replay (§3).

Unresolved:
- Whether `medium` effort or a Sonnet search helper keeps researcher quality (#262). The Anthropic research-effort numbers are for `low`.
- The lead's re-orientation cost after compaction (only 5 compactions in the window; #258).
- `low` effort for mechanical builder issues: Anthropic's cheapest policy is `low` with re-runs at `high` (97 % at $0.17), while r2-against warns that a lower default was reverted once at Anthropic; it stays behind an eval inside #259.
- Per-agent output and thinking cost: hidden thinking is spread evenly by assumption, and the subscription's per-model usage weighting is undocumented.
- Reviewer precision: no record of which findings were wrong (#83).
- The Haiku 5.5 side calls (0.4 % of spend) are priced at its up-to-100k prompt prices; their prompt lengths were not checked.

## 8. What not to do
Each is rejected on evidence ([r2-against](_scratch/harness-efficiency/r2-against.md) unless named):
- **No Sonnet or Haiku for security-reviewer or research-auditor.** The saving is about $82, 3.5 % of spend at the corrected cache price (VERIFIED, synthesis_checks.py §3), there is no same-family code-review recall measurement, and Anthropic says to keep judgment calls on the main model (§3, §4).
- **No brevity or narration caps between tool calls**, and no "budgets only fall" as a goal: the reverted 25-word line showed a 3 % drop on one evaluation (Opus 4.6 and 4.7), and our evals cannot see 3 % (§6). Keep the word-budget cap; a raise needs evidence and owner approval.
- **No round cap that merges with an open blocker.** After round 3 the approach is escalated; blocking findings never expire (§4).
- **No compaction of `dev check` or `cite-check` output**; `dev lit` changes only behind an A/B judged on cost per accepted note (§5).
- **No global effort cut**, and no lower effort for researcher, research-auditor or security-reviewer without an eval; Anthropic reverted a lower default once (SOURCED, [postmortem](https://www.anthropic.com/engineering/april-23-postmortem)).
- **No tool-result clearing, no 5-minute TTL for reviewers, no mid-session `/model` in the lead (an effort change keeps the cache on Opus 5.5), no `opusplan`, no fast mode for unattended workers** (§2, §3).
- **No moving rules into skills to save words**: skills mostly do not load (§5).
- **No note-size cap on cost grounds** (no size-cost association) and **no Monitor-for-`sleep` change as a cost lever** ($18) (§2).
- **No "verify twice", "think hard" or self-delegated verification prose** (§3).
- **Do not read this window as causal**, and do not cite the pre-harness comparison (27.6 M vs 4.5 M builder tokens; different repository and tasks) as a harness effect.
