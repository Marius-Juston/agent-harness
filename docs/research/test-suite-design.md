## 0. Findings in one paragraph
No test shape (pyramid, trophy, honeycomb) and no unit:integration:E2E ratio has outcome data behind it. Google's own guidance is 80/15/5 by count, and the often-quoted 70/20/10 is a blog's "first guess". What the data does show: suite size and assertion count predict fault detection better than coverage; unit and integration tests catch the same defect types, but unit tests localise faults better; large tests are about 28 times as flaky as small ones; and production escapes cluster at boundaries (error handling, data formats between processes, configuration, the real database or model or simulator). So the size-tiered rules below are about **cost and presence, not shape**. Every project type needs at least one enforced test across each boundary where its escapes cluster (§5), and the rest of the suite should be as small and fast as it can be. Flakiness is the constraint that binds as a suite grows. To keep spurious red runs at or below 5%, the per-test flake rate must fall tenfold for each tenfold growth in tests (5.1e-4 at 100 tests, 5.1e-6 at 10,000). Reruns cannot verify rates that low, so medium and large suites need an outcome ledger. Agents add specific risks: they edit or special-case tests (ImpossibleBench: about 50% on impossible tasks for GPT-5 and Claude Opus 4.1) and write weak oracles. Mechanical guards answer this better than an LLM reviewer: a weakening check, base-commit replay, and diff-scoped mutation. The four sibling repositories show each failure mode. L's CI was red for all 92 of its runs, and then Actions was disabled. In R, 14% of tests fail on a fresh clone. H has a stale floor that nobody acts on, and E's weekly maintenance job failed silently. **For #114:** build a deterministic `dev` audit command with an `orient` trigger, and file its mechanical findings as issues directly. Add a small read-only subagent only for the judgement items (missing E2E kinds, mutation survivors, oracle quality). The subagent differs from `harness-ops:tester`: it audits the whole suite and never edits tests.

## 1. Question and scope
How should an agent-run repository design and maintain its test suite as it grows: which kinds of tests, how many, which end-to-end tests are necessary, and how CI should run them? The answer serves #114 (a size-tiered suite audit) and the template's gate defaults. Out of scope: count and coverage floors and diff coverage ([test-floors-and-coverage.md](test-floors-and-coverage.md)).

## 2. What the evidence supports
- **Shapes are opinion.** SOURCED: the pyramid, trophy and honeycomb cite no outcome data. Fowler calls the debate "moot", because the camps define "unit" differently, and says the percentages are "a distraction" ([Fowler 2021](https://martinfowler.com/articles/2021-test-shapes.html)). The only shape-compliance study measured shape, not defects ([r1-theory-shapes](_scratch/test-suite-design/r1-theory-shapes.md) F1). A third, targeted search in round 2 found no study that links the test mix to escaped defects ([r2-e2e-by-type](_scratch/test-suite-design/r2-e2e-by-type.md) A1).
- **The Google ratio.** SOURCED: *Software Engineering at Google* says "around 80%" unit, 15% integration and 5% E2E, as "a very rough guideline", and it names the ice-cream-cone and hourglass antipatterns ([SWE book ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)). The 70/20/10 split is "a good first guess" in a 2015 blog post ([Wacker 2015](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)). Neither cites data.
- **Unit and integration tests find the same defect types.** SOURCED: Trautsch et al. classified 38,782 Java tests and compared them with mutation testing over five defect types. They "could not find any evidence that one test type is more capable of detecting certain defect types" ([JSS 2020](https://doi.org/10.1016/j.jss.2019.110421), abstract). The dissertation covers 27 Java and Python projects and finds that unit tests pinpoint the source of a defect better ([abstract](https://www.swe.informatik.uni-goettingen.de/node/2889)). The faults were mutants, not real faults. BELIEVED: classify tests by measurable traits (resources used, run time, test doubles, I/O), not by directory or name.
- **Test size predicts flakiness.** SOURCED: over about 4.2M Google tests in one week, 0.5% of small, 1.6% of medium and 14% of large tests were flaky. Flakiness tracked binary size (r² 0.82) and RAM (r² 0.76) more than it tracked the tool ([Listfield 2017](https://testing.googleblog.com/2017/04/where-do-our-flaky-tests-come-from.html), internal blog analysis with bucketed fits).
- **Size and assertions beat coverage.** SOURCED: once suite size is controlled, coverage correlates only weakly with effectiveness ([test-floors-and-coverage.md](test-floors-and-coverage.md)). The number of assertions correlates strongly with effectiveness (Zhang and Mesbah, FSE 2015, [Assertions are strongly correlated with test suite effectiveness](https://doi.org/10.1145/2786805.2786858), abstract). Mutants couple to 73% of 357 real faults, independently of coverage (Just et al., FSE 2014, [Are mutants a valid substitute for real faults in software testing?](https://doi.org/10.1145/2635868.2635929)). Mutation-score correlation with real-fault detection is weak once size is controlled, but the suites ranked top by mutation score still find more faults (Papadakis et al., ICSE 2018, [Are mutation scores correlated with real fault detection?](https://doi.org/10.1145/3180155.3180183), abstract). BELIEVED: use mutation as guidance and as an audit signal, never as a ratchet.
- **Most tests never fail; deleting them by coverage is unsafe.** SOURCED: of 5.56M Google test targets, 91.4% never failed in a month, and targets more than 10 dependency edges from a change "hardly ever break" ([Memon et al. 2017](https://research.google.com/pubs/archive/45861.pdf); share VERIFIED with [check_r1_against.py](_scratch/test-suite-design/scripts/check_r1_against.py)). Suites reduced by coverage missed every fault of up to 52.2% of 1,478 real failed builds ([Shi et al., ISSTA 2018](https://mir.cs.illinois.edu/gyori/pubs/issta18.pdf)). Predictive selection kept more than 99.9% of faulty changes caught at half the cost (Machalica et al. 2019, [Predictive Test Selection](https://arxiv.org/abs/1810.05286)). BELIEVED: select tests or move them to a later stage; delete only obsolete, change-detector or ownerless flaky tests.
- **Tests carry a measured cost.** SOURCED: in 61 Java projects on Travis, 18% of suite runs failed. 13% of those failures were flaky, and 26% of the non-flaky ones were obsolete or incorrect tests ([Labuschagne et al., FSE 2017](https://www.cs.ubc.ca/~rtholmes/papers/fse_2017_labuschange.pdf)). VERIFIED ([check_r1_against.py](_scratch/test-suite-design/scripts/check_r1_against.py)): that makes 36% of failing runs maintenance work rather than a found bug. Coding-agent commits add mocks to tests 36% of the time, against 26% for other commits, over 1.2M commits ([arXiv 2602.00409](https://arxiv.org/abs/2602.00409), preprint).
- **Density falls as projects grow.** SOURCED: across 20,817 GitHub projects, tests per LOC fall as LOC grows, Spearman ρ = −0.451 ([Kochhar et al. 2013](https://orbilu.uni.lu/bitstream/10993/15352/1/qsic-2013.pdf); "test" there means a test file). The median PyPI project has 3 tests (Gruber et al., ICST 2021, [An Empirical Study of Flaky Tests in Python](https://arxiv.org/pdf/2101.09077)). Test code grew from 10.8% to 21.9% of SLOC over two years in 61 Java projects, a test-to-production ratio of 0.28 ([Labuschagne 2017](https://www.cs.ubc.ca/~rtholmes/papers/fse_2017_labuschange.pdf)).
- **Property-based tests pay per test.** SOURCED: in 40 Python projects, each Hypothesis test found about 50 times as many mutants as the average unit test (Ravi and Coblenz, OOPSLA 2025, [An Empirical Evaluation of Property-Based Testing in Python](https://doi.org/10.1145/3764068), abstract). The figure is not normalised by run time.

## 4. Flakiness: the budget that tightens with size
- **Per-test budget.** VERIFIED ([flake_math.py](_scratch/test-suite-design/scripts/flake_math.py), independent tests assumed): to keep a run of N tests spuriously red at most 5% of the time, each test's per-run flake rate must stay at or below 5.1e-4 for N = 100, 5.1e-5 for 1,000, 1.0e-5 for 5,000 and 5.1e-6 for 10,000. Showing p < 5.1e-4 with 95% confidence takes 5,873 clean runs. BELIEVED: below the small tier, only a history of real gate runs is an affordable sample.
- **When flakes arise.** SOURCED: 75% of flaky tests were flaky when added, and checking new or changed tests catches 85% of them. The other 15% become flaky through changes elsewhere (Lam et al., OOPSLA 2020, [A large-scale longitudinal study of flaky tests](https://doi.org/10.1145/3428270)). In Python, test-order dependency causes 59% of flakes (Gruber 2021, [An Empirical Study of Flaky Tests in Python](https://arxiv.org/pdf/2101.09077)), so random order (pytest-randomly, already in H) targets the biggest cause. With 10 reruns, only about a quarter of flaky tests show up ([FlakeFlagger, ICSE 2021](https://doi.org/10.1109/icse43902.2021.00140)).
- **Quarantine grows unless capped.** SOURCED: Fowler suggests capping quarantine, for example "only allow 8 tests in quarantine" or "no longer than a week" ([Fowler 2011](https://martinfowler.com/articles/nonDeterminism.html)). Dropbox's automated quarantine "roughly doubled" within months ([Dropbox 2019](https://dropbox.tech/infrastructure/athena-our-automated-build-health-management-system)). Google's auto-quarantine "could easily mask a real race condition" ([Micco 2016](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)).
- **Red streaks.** SOURCED: across 27 projects, failing again in the next revision accounts for 42.9% of test failures, with a median persistence of 2 revisions, about a day (ESEM 2026, [Test Alert Snooze: An Empirical Study of Consecutive Test Failures on CI](https://doi.org/10.4230/lipics.esem.2026.24), abstract page). BELIEVED: a streak longer than 3 runs or 24 h is the tail worth an issue.

## 5. Necessary end-to-end tests by project type
SOURCED basis ([r2-e2e-by-type](_scratch/test-suite-design/r2-e2e-by-type.md)): production escapes cluster at boundaries.
- **Microsoft Teams.** In 152 high-severity incidents, postmortems most often named scenario tests (30.8%) and system tests (23.1%) as what would have caught the bug. Unit tests were named in 12.8% (Ghosh et al., SoCC 2022, [How to fight production incidents?](https://doi.org/10.1145/3542929.3563482); these are engineers' judgements, not measured catch rates).
- **Azure.** In 112 software-bug incidents, 31% were fault handling and 21% data format, and the data-format bugs were almost all cross-process ([Colyer's summary](https://blog.acolyer.org/2019/06/21/what-bugs-cause-cloud-production-incidents/) of HotOS 2019).
- **Distributed systems.** 92% of catastrophic failures came from mishandled errors that the software had signalled explicitly ([Yuan et al., OSDI 2014](https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-yuan.pdf)).
- **Coverage and field bugs.** Coverage has an insignificant correlation with post-release bugs across 100 Java projects (Kochhar et al. 2017, [Code Coverage and Postrelease Defects: A Large-Scale Study on Open Source Projects](https://doi.org/10.1109/tr.2017.2727062), abstract).

The rows below are BELIEVED syntheses. "Enforced" means the test runs in the gate, in a scheduled job or before a release. A test that exists only as an opt-in local command counts as absent; that is how L's PostgreSQL tier went unenforced.

An Empirical Study on Configuration Issues in Python PyPI Ecosystem](https://arxiv.org/abs/2310.12598), abstract); data-format escapes (above) |

**Why evals are not per-case asserts in the gate.** VERIFIED ([check_r2_e2e.py](_scratch/test-suite-design/scripts/check_r2_e2e.py)):
- With 50 cases that each pass 99% of runs, an all-must-pass gate is green only 60.5% of the time.
- A suite-level rule works better: with 50 cases, alarm at 44 or fewer passes. It raises a false alarm 3.8% of the time at a 95% baseline and catches a drop to 85% 78.1% of the time.

**Golden files carry an agent-specific risk.** BELIEVED: re-recording a golden file turns a red test green, which is a form of test weakening, so the weakening check must flag golden-file edits (#127).

## 6. CI/CD stages
- **Fast feedback.** SOURCED: developers should "get feedback from automated tests in less than ten minutes" ([DORA](https://dora.dev/capabilities/test-automation/)). Fowler's commit build "has to be done quickly", and a secondary stage hits a real database ([Fowler, CI](https://martinfowler.com/articles/continuousIntegration.html)). Google presubmit runs "only fast, reliable" tests; post-submit accepts longer times and some instability ([SWE book ch. 23](https://abseil.io/resources/swe-book/html/ch23.html)).
- **Test selection.** SOURCED: dynamic file-level selection is safe and cut test time by 32% on average ([Ekstazi, ISSTA 2015](https://doi.org/10.1145/2771783.2771784)). Static class-level selection is "unsafe sometimes" (Legunsen et al., FSE 2016, [An extensive study of static regression test selection in modern software evolution](https://doi.org/10.1145/2950290.2950361)). VERIFIED (read `devkit/gate.py`): H's `--affected` is static and misses indirect importers (#118). That is safe only because the gate always runs the whole suite.
- **Merge queues.** SOURCED: GitHub's merge queue became available to organization-owned public repositories and on Enterprise Cloud ([changelog 2023](https://github.blog/changelog/2023-07-12-pull-request-merge-queue-is-now-generally-available/); current eligibility BELIEVED unchanged). H and E are user-owned. BELIEVED: `uv run dev integrate` already re-gates the merged tree serially, and that is enough for one lead.
- **Free-tier minutes.** SOURCED: a private repository gets 2,000 minutes a month, rounded up per job ([Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)). VERIFIED ([ci_minutes_budget.py](_scratch/test-suite-design/scripts/ci_minutes_budget.py)): a 10-minute job plus 3 small jobs bills 13 minutes, which allows 153 runs a month, so fold small checks into one job. A daily 64-minute soak, as in L, would use 1,920 of the 2,000.
- **Scheduled work fails silently.** VERIFIED: E's first weekly maintenance run was red, and the step meant to file the issue failed on a body over 65,536 characters (#120). H's `slow` fresh-clone test runs in no CI job (#117).

## 7. Tests written by agents: what to guard
- **Gaming.** SOURCED: when tests contradict the spec, GPT-5 cheated on 54% of tasks and Claude Opus 4.1 on about 50%, mostly by editing tests. Read-only tests stopped the edits but not special-casing, and LLM monitors caught only 42-65% of the cheating ([ImpossibleBench, arXiv 2510.20270](https://arxiv.org/abs/2510.20270), Oct 2025). Codex, Claude Code (Sonnet 4) and Gemini CLI hard-coded test cases in 22-44% of runs on 9 ambiguous problems ([EvilGenie, arXiv 2511.21654](https://arxiv.org/abs/2511.21654)). These are older models; no rates for current ones were found.
- **Weak oracles.** SOURCED: LLM-written oracles mostly encode current behaviour, not intended behaviour ([arXiv 2603.23443](https://arxiv.org/abs/2603.23443): more than 99% of the tests that failed after a semantics-changing edit still passed on the old program). One study found Claude Sonnet 4.6 tests no worse than Django's or Pandas's (96.6% against 97.7% and 95.4% effective). The main failure mode in every corpus was a weak-value or loose-bound oracle ([arXiv 2608.15188](https://arxiv.org/abs/2608.15188), single author, not peer reviewed).
- **Gaps in agent PRs.** SOURCED: in 4,882 agent PRs, the existing tests ran none of the changed lines in 64.8% of the Python PRs, and the tests missed error-handling lines 81-86% of the time ([arXiv 2607.18057](https://arxiv.org/abs/2607.18057)).
- **Base-commit replay.** VERIFIED ([replay_new_tests.py](_scratch/test-suite-design/scripts/replay_new_tests.py), H's last 12 merges): 159 new or changed tests were replayed on each merge's base. 7.5% passed there legitimately (boundary and negative cases), 30.8% failed an assertion, and 61.6% failed only because the API did not exist yet. Every PR had at least one test that failed on its base. The replay costs 0.3-8 s of pytest per PR. BELIEVED: the useful rule is to warn when *no* new test of a fix or feature PR fails on the base. A per-test rule would misfire on legitimate boundary tests.
- **Weakening.** VERIFIED ([weaken_probe.py](_scratch/test-suite-design/scripts/weaken_probe.py), re-run at synthesis): `devkit/weaken.py` flags 3 of 11 kinds: a deleted assert, a test renamed out of collection, and an added skip. It misses loosened, trivial and swallowed asserts, conftest and pytest-config edits, golden edits, patching the module under test, and fewer parametrize cases (#127).
- **Diff mutation.** VERIFIED ([r2-mutation-diff](_scratch/test-suite-design/r2-mutation-diff.md) F2; [r2_mutation_math.py](_scratch/test-suite-design/scripts/r2_mutation_math.py)): on H's #107 (253 added lines), cosmic-ray's `cr-filter-git` kept 402 mutants and 99 survived, in 289 s. mutmut, which works per function, made 2,331 mutants and 1,096 survived, in 194 s. Whole-package mutmut on `devkit/` took 475 s cold, and its score was 0.636. SOURCED: Google surfaces at most about 7 mutants per change, one per line, after suppressing "arid" lines; before suppression, developers rated 85% of the mutants it surfaced unproductive (Petrović et al., TSE 2021, [Practical Mutation Testing at Scale](https://arxiv.org/abs/2102.11378)). BELIEVED: diff mutation is advisory on hand-back, capped at 40 mutants and 5 minutes, and never a gate.

## 9. Recommendation: size-tiered defaults
The tier is the higher of two measures (BELIEVED; both are the binding constraints in §4 and §6):
- by collected tests: small (S) under 1,000, medium (M) 1,000-5,000, large (L) over 5,000;
- by gate wall time: S under 2 minutes, M 2-10 minutes, L over 10 minutes.

A project with no tests yet uses production size instead: S under 5 KLOC, M 5-50 KLOC, L over 50 KLOC. Today H, R and E are S, and L is L.

| | Small | Medium | Large |
|---|---|---|---|
| **Kinds** | mostly small (in-process) tests; property tests on parsers and pure logic; the necessary E2E set of §5 | the same, plus a flake-tracked I/O tier (real DB, subprocess) | the same, with E2E and soak tiers marked and scheduled |
| **Counts** (audit signals, not gates; floors in [test-floors-and-coverage.md](test-floors-and-coverage.md)) | at least 80% of fix commits add a regression test; every explicitly signalled error path has a test; test:prod LOC ratio at least 0.3 | ratio at least 0.3, alarm on a relative fall over 10%; asserts per test tracked | ratio at least 0.5; single-oracle share tracked |
| **Mix** | do not gate on shape; 80/15/5 by count is a sanity check only | same | same; E2E only on critical paths |
| **Flake budget** (per test-run, for at most 5% spurious red) | 5.1e-4; 5 seeded reruns of the suite at audit time | 5.1e-5; 10 reruns plus the outcome ledger | 5.1e-6; ledger plus 10 isolated reruns of each id that failed since the last audit |
| **Quarantine** | `flaky` marker plus an open issue; cap max(3, 0.5% of tests); entries 14 days at most | same | entries 7 days at most |
| **Per change (gate)** | the full non-slow suite in random order with xdist; weakening check; replay warning | same; `--affected` and testmon for local iteration only | selected tests plus a fixed smoke set; the full suite moves to before merge |
| **Before merge** | `dev integrate` re-gates the merged tree | same | full suite on the merged tree |
| **Hand-back (advisory)** | diff mutation, capped at 40 mutants and 5 minutes | same | same |
| **Scheduled** | weekly `--full` plus live tests (#117) | nightly `--full`; whole-package mutmut weekly; evals | nightly full, slow, live and soak; quarantine report |

These trip-wires apply at every size:
- gate wall time over 10 minutes means move to the next tier's staging;
- main red for 3 or more runs or over 24 hours means an issue;
- any scheduled job that is red, or whose reporting step failed, means an issue;
- an id that passes in a fresh clone but not in the working tree, or the reverse, means an issue.

Bounds: the tier boundaries and the 0.3 and 0.5 ratios are judgement, anchored on the sibling repositories (1.10, 0.60, 0.22) and on industrial Java (0.28). No study gives outcome data for quarantine caps or for audit cadence.

## 10. Component shape for #114
The owner suggested a subagent. The evidence supports one only for the judgement part (BELIEVED). Most of the audit is mechanical, and §7 shows that mechanical checks beat an LLM reviewer: LLM monitors caught 42-65% of cheating, while a diff check catches test edits exactly. #111 reaches the same split for the architecture review (its note is on PR #126).

| Shape | Fits | Does not fit |
|---|---|---|
| `dev` command | the nine checks of [r2-suite-health](_scratch/test-suite-design/r2-suite-health.md) F8: flaky ids, quarantine, red streaks and staleness, fresh-clone parity, never-run tests, slow tests, ratio and oracle drift, stale floors, fixes without a test. Also: tier, due trigger, presence of marked E2E kinds for the declared project type, scheduled-mutmut trend. Under 2 minutes on H (VERIFIED, r2 F2); testable and deterministic | deciding which mutation survivors matter (about 10 of 40 of mutmut's were actionable on a hand read), whether an unmarked test is really a golden or journey test, and whether an oracle is vacuous |
| read-only subagent | the judgement items above, turned into a few issues with a measurable DONE WHEN; its own context for reading many test files | the trigger and the counts: an agent asked "is an audit due?" has no history to compare against |
| skill | two lines in `harness-ops:lead`: when `orient` says an audit is due, run the command, and dispatch the subagent only if the report has judgement items | running the audit: it would load into the lead's context, and its words cost every session |
| `harness-ops:tester` (existing) | building the issues the audit files: it writes tests for one issue in a worktree | the audit itself: the tester is scoped to one change and edits tests, while the auditor reads the whole suite and must never edit or delete a test (§7: agents game tests they can edit; deletions need the owner's `weakening-ok:`) |

Recommended (BELIEVED):
1. **`uv run dev suite-audit`.** It prints the tier and the nine checks with tier thresholds, and with `--file` it keeps one issue per failing check under a stable title, updated rather than duplicated and closed when clean. That is the template's `maintenance.yml` pattern, with bodies capped well under 65,536 characters. It reads the JUnit ledger (#121) and needs no other new dependency.
2. **Trigger in `uv run dev orient`, in the unit #111 found best at agent pace: first-parent commits, not days or merged PRs.**
   - An audit is due after 25 first-parent commits since the last audit (S and M) or 50 (L), when collected tests grow by 25%, or when a tier boundary is crossed. Days since the audit are shown for information only.
   - Red streaks and stale floors are a few git and `gh` calls, so `orient` shows them on every run.
   - The last audit's commit is kept in the footer of a "Suite health" tracking issue, so no state is committed.
   - Share the first-parent counter with #113's trigger.
   - At H's pace (32 first-parent commits in its first 2 days, VERIFIED with `git rev-list --first-parent`), that is an audit every few days. A clean audit files nothing.
3. **A `harness-ops:suite-auditor` subagent.** It is read-only (Read, Grep, Glob, Bash) and is dispatched only when the report has judgement items. It files at most 5 `type:test` issues per audit, and the existing tester or builder takes them. It never edits tests.
4. **Not part of the audit, but filed with it:**
   - per change: the weakening extension (#127) and the replay warning (#133);
   - on hand-back: advisory diff mutation for the builder and the reviewer, as L runs it (#134);
   - for the gate: a JUnit ledger (#121), a reproducible seed (#119), `xfail_strict` and the stale floor (#136);
   - for H's own suite: an installed-wheel smoke test and golden tests of machine-read output (#132).

Bounds:
- The thresholds rest on four repositories, two of them days old. Recalibrate after 10 audits.
- No audit has yet been run end to end. #114's DONE WHEN asks for one, on H.
