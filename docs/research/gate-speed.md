Status: v1 (2026-11-19). Issue: #520. Serves #531, #532, #533 and the build issues #541-#544.

## 0. Findings in one paragraph
On a lightly loaded machine (2026-10-22 and 11-01, 37 merged integrates), an integrate took a median **217 s**, and **70.5 %** of the summed time was **waiting for GitHub Actions** (median 147.5 s per PR: the PR head's checks before the gate, or the merged tip's after it). The merged-tree gate was 26 s (11 %), the `--local-ci` stand-ins 20 s (7 %), and the wait for the gate slot 0 s. On 2026-11-19, with about 12 builders and research benchmarks on the 32-core machine (load average 43-122), the picture inverted. Passing gates took a median **82 s** of stage time against 25 s before (the test count was flat). One integrate gate took 918 s. Worker gates waited a median 162 s (p90 1257 s) for the single slot. A 3-PR chain took **1946 s**: 54 % gate stages, 33 % waiting on Actions or a failed GitHub call, and 4 % slot wait. Two things drive the time, and neither needs weaker verification. (1) **Actions on the critical path of every merge.** Local-first CI (#531) removes a median 147.5 s per chain member when Actions run, and up to 600 s (`local_ci_wait_s`) when they never start. Its stand-in must first gain the ci job's gitleaks, audit and live security steps (#544, about +40 s), or local merges skip them. Where Actions stay in the loop, running the gate concurrently with them saves a median 45 s (#541). (2) **CPU contention and network waits inside the gate.** The board stage holds the one slot for 10-30 s of network reads and can never fail a gate (#542). Non-gate work at normal priority inflates a 25-43 s gate to 54-918 s (#543: nice it, BELIEVED up to 40-57 s per gate). Reusing the builder's pass (#533) saves at most 15 s per PR at light load; chains rarely hit it, because every merge moves main. Speculative train gating (#532) saves about 1 s per PR at the measured 1-in-45 merged-tree failure rate. Rank both last.

## 1. Question and scope
Owner, 2026-11-19: the gate and integrate take far longer than development; speed them up drastically without letting broken code reach main. A follow-up the same day asked about chains of PRs when Actions minutes run out. Scope: a measured timeline of integrates (pre-gate, slot wait, gate, stand-ins, post-gate) and of worker gates (slot wait, stages, slowest tests). Also: Actions timings, chain throughput, and for each candidate its saving and what verification it gives up. Out of scope: building the changes (the build issues in Follow-ups).

Method (VERIFIED, scripts in [_scratch/gate-speed/scripts/](_scratch/gate-speed/scripts/summarize.py); no full gate was run for this note):
- [transcript_gates.py](_scratch/gate-speed/scripts/transcript_gates.py) reads the lead's and subagents' Claude Code transcripts for this repository. For every `dev check` and `dev integrate` Bash call it records the call time, result time and RESULT line.
- [integrate_timeline.py](_scratch/gate-speed/scripts/integrate_timeline.py) joins the integrate calls that ended `merged` to the integrate logs in the shared state dir: a log's birth time is the gate's start, its last write the end of the stand-ins. It also joins the outcome records (their write time is the merge). Phases: **pre** (call to log created: feedback reads, the wait for checks still running on the PR head, fetch, merge, regenerate), **lock** (slot wait), **gate** (the gate's own RESULT seconds), **stand-in** (the rendered project's gate seconds plus 19 s, timed separately by [time_standins.sh](_scratch/gate-speed/scripts/time_standins.sh): render_check 14.8 s, two plugin validations 5.3 s and 6.2 s), **post** (stand-ins done to outcome written: Actions on the merged tip, feedback re-read, merge, issue closing).
- [worker_gates.py](_scratch/gate-speed/scripts/worker_gates.py) times worker gates. It also follows calls Claude Code moved to the background, by their task output file.
- [actions_runs.py](_scratch/gate-speed/scripts/actions_runs.py) takes job and step durations of 40 `ci` runs from `gh run view`.
- [time_stages.py](_scratch/gate-speed/scripts/time_stages.py) and [time_board.py](_scratch/gate-speed/scripts/time_board.py) time each non-test stage outside the lock.
- [cpu_by_project.py](_scratch/gate-speed/scripts/cpu_by_project.py) samples which repositories use the CPU.
- [summarize.py](_scratch/gate-speed/scripts/summarize.py) prints every number below into [summary.txt](_scratch/gate-speed/summary.txt), and [chain_case.py](_scratch/gate-speed/scripts/chain_case.py) the 2026-11-19 chain.

Caveats (VERIFIED unless marked):
- The machine clock ran 1 h behind GitHub's on 2026-11-01. Durations within one clock are unaffected; the offset was used only to match integrates to Actions runs by hand.
- Integrate calls run in the background were skipped, except the 2026-11-19 chain, which was read from its task output.
- 2026-11-19 has only 10 worker gates and 3 integrates with full data, because most calls there ran in the background and their outputs were tailed.
- Per-stage times inside a recorded gate do not exist (#521 adds them), so the test stage's share is inferred.

## 2. Integrate timeline (37 merges, light load, Actions available)
VERIFIED ([summary.txt](_scratch/gate-speed/summary.txt), section 1). 29 of the 37 ran with `--local-ci`.

| phase | median | p90 | share of summed wall |
|---|---|---|---|
| wall (call to result) | 217 s | 346 s | 100 % |
| pre (incl. wait for running checks on the PR head) | 125 s | 154 s | 42.0 % |
| lock (gate slot) | 0 s | 1 s | 0.2 % |
| gate stages | 26 s | 28 s | 11.2 % |
| `--local-ci` stand-ins | 20 s | 21 s | 6.9 % |
| post (incl. wait for Actions on a pushed tip) | 33 s | 215 s | 43.3 % |

- **Actions wait dominates.** Pre-gate time with no check to wait for was a median 10 s; post-gate time with nothing pushed was 24.5 s. The rest of pre plus post is waiting for Actions: a median **147.5 s** per integrate (p90 256.5 s), **70.5 %** of all integrate time. Which wait applies depends on the PR. In 22 of 37 (59 %) the PR already contained main, and integrate waited a median 139.5 s before the gate for checks still running on the head. The lead had integrated right after the builder's push: for PR #484 the run started at 09:31:15Z, finished at 09:34:05Z, and the pre phase was 159 s. In the other 15, integrate pushed the merged tree and waited a median 197 s after the gate for the checks on that new tip. Either way, a full Actions run sits on the critical path of every merge.
- **The Actions run itself** (40 `ci` runs, 2026-11-01..19; VERIFIED, [summary.txt](_scratch/gate-speed/summary.txt) section 3): queue 2 s, run wall median 158 s (p90 177 s). The `check` job took 155.5 s: its gate 101 s on the hosted runner and gitleaks over history 36.5 s. `template` took 15.5 s and `plugin` 11.5 s. One run took 3761 s (a hung `check` job). Actions start within seconds when they can run. The wait is the job itself, about 6 times the local gate.
- **Chain throughput.** On 2026-11-01 the lead merged 39 PRs in 6.19 h, one every 571 s. Integrate calls took 10,806 s of that span (48 %); the rest is the lead's own work between merges. Rework from failed integrates cost 533 s (5 %): one merged-tree gate failure (79 s), one conflict (342 s) and four refusals (112 s). VERIFIED from [transcript_gates.py](_scratch/gate-speed/scripts/transcript_gates.py) output.
- **When Actions cannot run** (no such integrate in these logs, so this is the code path, VERIFIED by reading `devkit/ci_status.py`). A job that a billing block ends with no steps is detected at once (`never_ran`). A check that stays queued, or never registers, is waited for `local_ci_wait_s` = 600 s per chain member before integrate stands in. Which of the two a spending limit produces is ASSUMED unknown; #531 detects it within 30 s.

## 3. Worker gates and the gate's own stages
VERIFIED ([summary.txt](_scratch/gate-speed/summary.txt) sections 2, 4, 5).

| period | worker gates | wall median (p90) | stage median (p90) | wall minus stage, median (p90) |
|---|---|---|---|---|
| 2026-10-20..11-01 | 118 | 28 s (44 s) | 25 s (28 s) | 2 s (21 s) |
| 2026-11-19 | 10 | 261.5 s (1326 s) | 90.5 s (156 s) | 162.5 s (1257 s) |

- **Pass records** (every passing gate, worker or integrate) give the same picture. The median stage time was 25 s from 2026-10-20 to 11-01 (n = 147, max 37 s), 43 s for the single pass of 2026-11-17, and 82 s on 2026-11-19 (n = 7, p90 102 s, max 918 s). The suite did not grow to match: 2371-2431 tests on 11-01 and 2432-2448 on 11-19. The summed per-test seconds rose from a median 121 s to 194 s (max 327 s) for the same tests, so each test ran slower. That is contention, not new work.
- **The machine on 2026-11-19.** Load average 43-122 on 32 cores while this note was measured. A 4 x 5 s sample ([cpu_by_project.py](_scratch/gate-speed/scripts/cpu_by_project.py)) found 18.5-31.2 busy cores. 15-27 of them were research benchmark scripts in this repository's worktrees and 3-4 were test runs (this repository's and another project's). `gate_slots` bounds gates of one repository only. `dev test`, direct pytest, research scripts and other projects' gates all compete with a gate at the same priority. The sample is a snapshot (VERIFIED for that minute); the heavier mix during the 17:28-18:00 gates is not recorded.
- **Non-test stages** (timed outside the lock, three runs; [time_stages.py](_scratch/gate-speed/scripts/time_stages.py)). The board stage ("board conventions (warnings only)") took **18.9, 30.1 and 24.2 s**. Its parts took 9.2-10.4 s in two more runs ([time_board.py](_scratch/gate-speed/scripts/time_board.py): issue fetch with comments 6.1-6.4 s, `merged_closes` 3.0-4.0 s). Every other non-test stage summed to under 3 s: doc links 0.4-0.7 s, dev commands 0.5-2.0 s, ruff 0.6 s, the rest under 0.3 s each. The board stage reads 180 issues over the network while holding the machine's only gate slot, and by its docstring it cannot fail a gate (`devkit/board.py` `check_board`: "Findings are warnings"). In PR #493's 918 s integrate gate its read failed with a TLS handshake timeout. That run's per-test durations sum to 244 s (CPU-seconds over all workers), so at least ~670 s of the 918 s went outside the tests' own durations. Without per-stage times (#521) the exact place is unknown; a gh call with no timeout is the BELIEVED cause.
- **Fixed costs around the stages.** The pass fingerprint (`gate.selection`, a second `pytest --collect-only`) took 4.7-9.8 s under load and 2.6-3.6 s in quieter minutes, run serially after every passing gate. Collection costs about 1.9 s of CPU per process, so a 16-worker xdist run spends about 32 CPU-seconds collecting.
- **Slowest tests.** No test is slow. On 11-01 the slowest had a median of 3.58 s, 21 tests took over 1 s, the top 10 tests held 20 % of the summed test seconds and the top 50 held 45 %. On 11-19 the figures were 3.95 s, 28 tests, 19 % and 43 %. The heaviest files are test_hooks, test_gate, test_template and test_train. On 16 workers the critical path is a few seconds, so moving "slow tests" out of worker gates would save little wall time (BELIEVED).

- **Why #543 should work (SOURCED, single-source).** The Linux CFS scheduler weights nice levels multiplicatively. "running a nice +10 and a nice 11 task has the same CPU utilization 'split' between them" as two tasks one level apart anywhere: "(one will get 55% of the CPU, the other 45%.)", and "nice +19 tasks get a HZ-independent 1.5%" ([CFS Scheduler: Scheduler Nice Design](https://docs.kernel.org/scheduler/sched-nice-design.html), Linux kernel documentation, sections on the "multiplicative" nice levels). So work ten levels lower gets a small fraction of what the gate gets, and no root is needed to lower one's own priority. The size of the saving here is unmeasured until #543's DONE WHEN measures it.
- **Why speculation ranks last (SOURCED, single-source).** Uber's production merge queue speculatively builds the likely outcomes of pending changes. Its 2025 follow-up says the system "faces inefficiencies in resource utilization, leading to a high rate of premature build aborts". After adding prediction and a speculation threshold so that "only the most likely builds are executed", it reports "a reduction in Continuous Integration (CI) resource usage by approximately 53%, CPU usage by 44%, and P95 waiting times by 37%" (Juloori et al. 2025, [CI at Scale: Lean, Green, and Fast](https://arxiv.org/abs/2501.03440), ICSE-SEIP, abstract). The original system's goal is the same as the owner's: "always green master, high throughput, and low commit turnaround time" (Ananthanarayanan et al. 2019, [Keeping Master Green at Scale](https://doi.org/10.1145/3302424.3303970), EuroSys, abstract). Speculation pays when builds fail often and spare machines exist. Here merged-tree failures were about 2 % and the CPU was saturated, so extra concurrent gates would slow every gate (BELIEVED).
- **On test selection (SOURCED).** Shi, Zhao and Marinov compared module- and class-level selection on real Travis builds. Selection saved time, but a full build with it still took 76.0 % of the time of running everything, "due to the extra overhead in a cloud-based CI environment". The failures it skipped were "almost all flaky test failures" (2019, [Understanding and Improving Regression Test Selection in Continuous Integration](https://doi.org/10.1109/issre.2019.00031), ISSRE, abstract). A coverage-based Python tool missed 0-2 % of mutation faults at file level (Kauhanen et al. 2021, [Regression Test Selection Tool for Python in Continuous Integration Process](https://doi.org/10.1109/saner50967.2021.00077), SANER, abstract). [test-suite-design.md](test-suite-design.md) §5 already keeps the full suite in the gate at this project's size; this note does not change that.
- **Actions minutes.** "The use of standard GitHub-hosted runners is free: ... In public repositories" ([GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions), GitHub Docs, "Included compute usage and storage"). A private project on GitHub Free gets "$12 USD" a month of included compute (same page). This repository is public, so its runs are free (SOURCED). The owner's limit therefore bites in private projects that pin the harness, which is where #531's `ci = 'local'` mode matters most (BELIEVED). A merge here triggers about three `ci` runs per PR (the builder's push, integrate's pushed tip when the PR is behind, main's push), each about 3 job-minutes (VERIFIED from [summary.txt](_scratch/gate-speed/summary.txt) section 3 and the run list). Local-first CI drops the middle one and makes the first optional.

## 5. Recommendation for this project
Do these in order. Each keeps "nothing reaches main without passing the full gate on the exact merged tree" intact.
1. **#544, then #531.** Make the local stand-in equal to the ci `check` job: add gitleaks history, `uv audit` and the live security tests (about +40 s per local integrate). Then let integrate stop waiting for Actions (`ci = 'local'`, or instant detection when Actions cannot run). Expected chain throughput at light load: about 217 s per member falls to about 110 s (147.5 s Actions removed, about 40 s added). When Actions are out of minutes, up to 600 s more per member is saved. Actions remain a post-merge backstop on main's push. The bound: a failure only a clean hosted runner shows reaches main and is caught about 160 s later (ASSUMED rare: all 59 completed `ci` runs since 11-01 succeeded, VERIFIED with `gh run list`, so none caught what the local gate missed).
2. **#543 and #542** (every gate, worker and integrate). Run non-gate work at `nice +10`. Take the board read out of the gate and put a 60 s timeout on gate gh calls, so a 25-43 s gate stays near that under load instead of 82-918 s. Re-measure with #521's per-stage times. DONE when the 2026-11-19-style load gives gate stage times within 1.3 x of idle.
3. **#541** while Actions stay in the loop (the default `ci = 'actions'`): gate concurrently with the Actions wait, a median 45 s per merge.
4. **#523/#474 (slots)** only after 2: more slots split the same cores (`workers()` divides cores by slots) and do not help a saturated machine (BELIEVED). Size them from free CPU, not core count.
5. Hold **#533** and **#532**. #533's saving is at most 15 s at light load, rarely hits in a chain, and gives up the one independent clean run. #532 saves about 1 s per merge at today's failure rate. Revisit both when #531 and #543 have landed and a train merges routinely.
