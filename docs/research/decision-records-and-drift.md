## 0. Findings in one paragraph
**Projects run for months (#282).** The costliest drift on record is version skew, and it needs an exact check, not a sweep. A downstream project's agents ran the harness plugin's 0.1.4 build for 162 h while its pin moved from v0.1.5 to v0.1.9. In that time 305 of 491 plugin subagents ran an agent body older than the pin, 92 of 96 builder spawns ran without the completion gate, 27 of 29 `uv add` calls ran without the reuse guard, and no session ran v0.1.9. The cause is Claude Code's per-user marketplace registry, not #163. `doctor` warned with exit 0 and was never run after the first day, and the installed version string does not identify the build: both install records on this machine name a version whose tag is a different commit. A content-digest check in the plugin's own SessionStart and SubagentStart hooks would have fired at 10 of 10 session starts, the first 1.35 h after the pin moved. Instruction files barely drift mechanically: 3 break episodes in 990 merges, all false, and 16 of 17 invalidated claims were fixed in the same merge. Specs and docstrings do drift. L3 had 52 true spec episodes, and the 34 that were fixed took a median 90.7 days, 31 of them by deleting the doc. An LLM claim sweep reached 0.87 precision on drifted docs but 0.22 on maintained instruction files, so it belongs on specs and docstrings only, as an advisory sweep. In auto memory, 8 of 34 checkable entries were stale within 3 weeks, half of them within a day of writing, and 6 were never corrected. No harm traces to staleness. The one harm is scope: a user-wide preference stored in one project's memory never reached this repository, and 170 of its 310 commits since then carry the trailer it forbids. 91% of subagents carry the lead's memory index, against the docs. Standing warnings decay: one project's session-start lint count rose from 72 to 138 in three days, and two "due" lines were shown 80 and 62 times with no action. The ranked additions (§14.1):
1. a loaded-root skew check;
2. write-time memory provenance and user scope, with orient printing only flagged entries (#233 re-scoped);
3. warnings printed only when new or rising;
4. an advisory LLM sweep for specs and docstrings, with delete-or-regenerate as the default fix;
5. #229 kept a warning that skips research notes and negative references.

Months-scale memory drift is unobservable here (transcripts are kept 30 days, and no entry is older than 23 days), and every label has one rater.

**Decision records and drift at every level (#220).** Do not ship ADRs: ship a smaller decision mechanism (tests and hooks, one checked decision table, a board-lint warning), and gate only the drift checks that were exact on history. In H's whole history (2026-10-11 to 13), 23 decisions were made in issue and PR comments; 5 (22%) exist only in comments and 6 changed an issue's scope without editing its DONE WHEN. Of 5 reversals, the one that needed a check (C1: the reason behind "never curl the literature APIs" deleted to fit a word budget, restored 8 h later) is caught by a literal marker on the reason. An ADR directory, path-scoped `.claude/rules/` and a decision-labelled issue index each prevent 0 of the 5 beyond that marker. The path-scoped rule was not even loaded when C1 happened: the deletion was a scripted Bash edit, and at most 19% of Bash writes in 242 transcripts were "cold" in the same way (an upper bound). Project B, which has ADRs, showed decay within 3 days: one ADR amended in place, one cited nowhere, and a research note that contradicted a policy ADR for about 14 hours until a research round, not the ADR, caught it. Agent evidence for decision records is real but weak and unreplicated, and it favours a short "why" next to the rule over a separate document. The minimum set is: (1) tests and hooks first (they already hold 10 of 23 decisions), plus a hook that denies direct curl, wget or WebFetch to the five literature API endpoints `uv run dev lit` wraps (replayed over 244 transcripts it blocks 236 direct calls and no article page); (2) one `.devkit/decisions.toml` table (rule, why-link, `enforced-by` literal on the reason, status), checked in about 30 lines and rendered as a linked, never-loaded index (while the check is a warning it stops a C1-style deletion only if the lead reads the warning at integrate; the hook holds C1's harm either way); (3) a `board lint` warning for scope decided in comments. Of 32 historical drift classes across the two repositories, today's checks would still miss 17. Replayed over every merge, three proposed checks raised zero false positives: deleted Owns paths under open issues (11 of 11 flags real, 1 root event) becomes a gate; `uv run dev` spans with flags and positionals (1 true event, 0 FP) stays a warning until a held-out replay, because its syntax rules were fitted on the same history; and integrate writes the test floor (9 raises, 0 false failures). DONE WHEN ticks and HANDOFF live state should be generated, not checked (0 ticked boxes in 451 body versions; prose checks of HANDOFF were 20% precise). Markers and `.py` spans stay warnings, decision-level drift needs an advisory step beyond markers, and links go to a weekly sweep with a fixed lychee config (0 of 539 reported URLs were verifiably dead). Every precision rests on 0 or 1 real events and was measured in-sample, so no warning becomes a gate before a held-out replay over the next 30 merges.

## 1. Question and scope
The questions ([QUESTION.md](_scratch/adr-drift/QUESTION.md)):
1. Should agent-harness and its template ship ADRs, and if so with what format, trigger, discovery, supersession and gate check?
2. What drifts at each level of a harness-run repository, what does each level have today, and what is the cheapest reliable enforcement?
3. (Owner, before round 2.) Is there something better than ADRs for an agent-run repository? Candidates: executable decisions, path-scoped rules, hooks, inline rule plus reason plus `enforced-by` marker, decision-labelled issues with a generated index, and ADRs as the baseline. ## 3. ADRs and the alternatives
### 3.1 Evidence on ADRs with human teams (SOURCED)
- Adoption is low, and about half of GitHub repositories with ADRs hold only 1 to 5, "tried but not yet definitively adopted"; systematic use is a team activity over a long period (Buchgeher et al., IEEE Access 2023, [Using Architecture Decision Records in Open Source Projects—An MSR Study on GitHub](https://doi.org/10.1109/access.2023.3287654), abstract).
- In a sample of 5,435 of the 116,211 AIDev agent-active repositories, ADR or decision-log directories appear in 0.9-1.9% of repositories per visibility stratum, which the authors call lower bounds (Díaz et al. 2026, [Methodological Harness in Agentic Software Engineering: An Empirical Study on Mining Software Repositories](https://arxiv.org/abs/2609.32014), preprint; the rates are in the full text's Results table, read through the arXiv MCP, not in the abstract).
- In 4,316 ADRs from 547 projects, "alternatives, decisions drivers, and some quality concerns remain under-documented" (Miccio Palermo et al. 2026, [A Text Mining and Classification Approach for Analyzing Architecture Decision Records](https://arxiv.org/abs/2609.07375), preprint).
- A 3-month industrial introduction improved documentation culture but left distributed-systems problems open, and where records are stored shaped their usefulness ([Ahmeti et al., ECSA 2024](https://research.chalmers.se/en/publication/542849), abstract).
- Nygard's format beat MADR on comprehension in a student experiment (Nogueira et al. 2026, [One Size Fits All? An Empirical Comparison of ADR Templates regarding Comprehension, Usability, and Ease of Adoption](https://arxiv.org/abs/2604.27333), preprint, N not in the abstract). Formats: [Nygard 2011](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions) and [MADR](https://github.com/adr/madr/blob/develop/template/adr-template.md).
- No study found measures how often recorded decisions are reversed or re-argued, for humans or agents (BELIEVED absence, from the round-1 searches).

### 3.2 Evidence with coding agents (SOURCED; all 2026, model-dated, none replicated)
- With ADRs served over MCP, one 12.5-turn TypeScript build took 10.1% less time and wrote 16-25 E2E tests where the plain run wrote 0; one project, the tool's author, no statistics ([Kitayama, TechRxiv](https://doi.org/10.36227/techrxiv.177205025.54351571/v1), abstract).
- Retrieval of recorded product decisions raised Claude Code's decision compliance from 46% to 95% over 8 tasks, but the decisions were designed by the authors to be invisible in code and there is no read-all-ADRs baseline ([Dillon and Varanasi](https://arxiv.org/abs/2605.08112), §7.6).
- A pre-registered study of a versioned decision file found +26 pp localization for a small executor given context from a stronger model, and a frontier gain of +14.6 pp that lost significance after Holm correction (p = 0.081) ([Kerbel et al.](https://doi.org/10.1145/3843282.3844425), abstract).
- Contrary: over 288 runs of Claude Code and Codex on 17 real tasks, context files did not change correctness, bounded to at most 10-15 pp by equivalence testing ([Khatri 2026](https://arxiv.org/abs/2607.27250), abstract).
- LLM checks of ADR compliance were weakest on organizational and process decisions, F1 0.71-0.79, on 980 ADRs from 109 repositories (Su et al., ICSA 2026, [Evaluating Large Language Models for Detecting Architectural Decision Violations](https://arxiv.org/abs/2602.07609)). H's at-risk decisions are of that kind.
- Rationale comments removed 99.3% of excess instructions in synthetic worlds, and the deletion hazard of agent instructions falls with age (log-hazard -0.032 per commit, 95% CI -0.047 to -0.019) over 247,694 instruction lifetimes ([Chakrabarti 2026](https://arxiv.org/abs/2608.11095)).
- An added rule in an Agent Skill raised the rate at which four coding agents took the required action by +0.23 on average, mainly for rules that name a command or path; when the Skill body loads only on demand, as in real tools, the agents kept about half (51%) of that gain (Wang et al. 2026, [Agent Skill Evolution: How Revisions Affect Coding Agents](https://arxiv.org/abs/2610.04832), abstract).
- Weak evidence for ADRs as agent guardrails: a design-science study that used executable requirements, C4 models and ADRs reports less implementation drift than unstructured or prompt-engineered development of one web application (Lipsanen et al. 2026, [Shift-Up: A Framework for Software Engineering Guardrails in AI-native Software Development -- Initial Findings](https://arxiv.org/abs/2604.20436), abstract; exploratory, no numbers in the abstract).
- BELIEVED synthesis: the benefit sits on decisions an agent cannot infer from code (owner policy, rejected alternatives, the reason for a rule). That favours a short reason next to the rule, in the file the agent edits, over a separate document read on demand.

### 3.3 Path-scoped rules miss the edit that mattered (SOURCED docs; VERIFIED probe)
- A rule with `paths` loads when Claude uses Read, Write or Edit on a matching file, or a Bash read such as `cat`; an invalid glob matches nothing silently; and rules are "context, not enforced configuration" ([memory docs](https://code.claude.com/docs/en/memory#path-specific-rules)).
- Probe on Claude Code 2.1.296 ([r2_rules_probe.sh](_scratch/adr-drift/scripts/r2_rules_probe.sh)): loaded on Read, `cat`, `sed -n` and Write, and inside a subagent; not loaded on Grep, `python3 -c "open(...)"` (the same class as `uv run dev code show`) or a denied Read. Haiku ignored a loaded rule in 4 of 7 loads as text "from the tool result"; Opus followed it in 3 of 3.
- In 242 transcripts ([r2_rule_triggers.py](_scratch/adr-drift/scripts/r2_rule_triggers.py)), 32% of reads (2,006 of 6,211) would load a rule, and 118 of 619 Bash writes with an extractable target (at most 19%) came before any loading access. The Bash-write heuristic was right on 16 of 30 sampled matches, so these are upper bounds.
- C1 was cold: the builder's only earlier access to the file was `grep -n`, the deletion was a `python3` heredoc that then ran the gate's ratchet check, and its first loading read came 62 s later ([r2-mechanisms M3](_scratch/adr-drift/r2-mechanisms.md)). BELIEVED: even a loaded rule would have lost to a failing word-budget gate; only another gate check changes that outcome.

### 3.5 Answer: no ADRs; the minimum mechanism (BELIEVED, from 3.1-3.4)
1. **Test or hook first** for any decision code can check. Add the missing test for D02 (no personal data in literature queries) and a PreToolUse hook that denies Bash `curl`/`wget` and WebFetch to the endpoints `uv run dev lit` wraps (§5, check 9), with a reason naming `uv run dev lit` and allow-list tests. The hook holds C1's harm whatever the prompt says.
2. **One decision table**, `.devkit/decisions.toml`. Each row: `id`, `rule` (one line), `why` (an issue, comment or note link), `enforced-by = [{path, literal}]` and `status = active | superseded` (with `by` when superseded). The literal is 5 words or fewer and taken from the **reason**, not the rule wording (§5, check 7). The check reports rows examined (zero fails per `ran.py`) and flags an active literal missing from its path. Removing one means flipping the row in the same PR, which makes the reversal explicit. While the check is a warning (§14.2), a C1-style deletion is stopped only if the lead reads the warning at integrate. `uv run dev docs` renders `docs/generated/decisions.md`, linked from HARNESS and never imported. The template ships an empty table and the check.
3. **A `board lint` warning** when an open issue's newest lead or owner comment is newer than its last body edit and says DONE WHEN, scope or decided. Scope decided in a comment then has to be written into the body.
4. **Not now:** a template ADR directory (no reversal prevented beyond the marker, and the largest drift surface) and path-scoped rules for decisions. A project that keeps ADRs for owner policy points a row's `why` at the ADR, and the table enforces it. The unique ADR numbers of [#63](https://github.com/Marius-Juston/agent-harness/issues/63) are then a project concern, not a template one.

## 5. Each proposed check, replayed over history (VERIFIED, [r2-replay](_scratch/adr-drift/r2-replay.md))
Method: every check ran at every first-parent merge (H 69, project B 56), against that commit's own state and parser, with issue bodies rebuilt from GitHub's edit history. A flag is TRUE when someone later had to change text, issues or code because of it. The bar for a gate is zero false positives on history: Google's compiler checks require "no effective false positives", and review checks tolerate up to 10% ([Sadowski et al., CACM 2018](https://6826.csail.mit.edu/2020/papers/google-analysis-cacm.pdf); SOURCED).

## 6. Why no semantic (LLM) drift check (SOURCED; BELIEVED)
- The best measured just-in-time README drift detector reached 75% precision (244 TP, 81 FP over 6,000 commits, 1.35 false alerts per 100 commits), and 26% of its true bugs were external references that change with no commit ([READU](https://arxiv.org/abs/2607.15780), Table II).
- A configuration-smell study measured 93.5% precision for a syntactic smell and 57% for the semantic "Conflicting Instructions" (dos Santos et al., SCAM 2026, [Configuration Smells in AGENTS.md Files: Common Mistakes in Configuring Coding Agents](https://arxiv.org/abs/2606.15828)).
- BELIEVED: an agent treats a failing check as a work order, so a false alert means editing correct text or weakening the check, the gaming pattern of [agent-harness.md §4](agent-harness.md#4-gaming-and-integrity-sourced-verified-in-repository-a). Semantic judges are sweep inputs at most, re-measured whenever the model changes. No study found measures how agents react to false-positive doc checks. #282 measured one such sweep (§10) and keeps it advisory, on specs and docstrings only.

## 8. Version skew between the pin and the loaded plugin (VERIFIED; cause SOURCED)
The costliest drift on record ([r1-platform-and-skew](_scratch/long-running-drift/r1-platform-and-skew.md) F1-F7).
- **What ran.** repo-E's pin (the marketplace `ref` in its settings) moved 8 times, v0.1.1 to v0.1.9, from 2026-10-11 to 10-15, while its install record stayed at 0.1.4. Its agents ran the plugin's 0.1.4 build for 162.4 h after the pin passed it (1.5 + 9.8 + 39.5 + 111.6 h across four pins, [skew_summary.py](_scratch/long-running-drift/scripts/skew_summary.py), sum checked in [synth_arith.py](_scratch/long-running-drift/scripts/synth_arith.py)). Matching each subagent's system prompt against every shipped agent body: 305 of 491 plugin subagents (62%) ran a body older than the pin, and 0 ran v0.1.9 ([skew_scan.py](_scratch/long-running-drift/scripts/skew_scan.py)).
- **What it cost.** `v0.1.4..v0.1.9` changed 17 plugin files in 26 PRs. In the window, 92 of 96 builder spawns ran without the completion gate and 27 of 29 `uv add` calls without the reuse guard ([skew_impact.py](_scratch/long-running-drift/scripts/skew_impact.py)). Skew fails silently: no "agent type not found" error occurred after the migration day (F6).
- **Why.** Not [#163](https://github.com/Marius-Juston/agent-harness/issues/163): repo-E moved its pin at every release. Claude Code keeps "one `known_marketplaces.json` per user", identifies a marketplace by its `name`, leaves background auto-update off for third-party marketplaces, and gives "a new copy of a plugin only when its computed version changes" ([plugin loading](https://code.claude.com/docs/en/plugins/loading), [host a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace), [plugin CLI](https://code.claude.com/docs/en/plugins/cli-reference); SOURCED). Re-adding a marketplace exits 0 as "already on disk", so `uv run dev setup` re-pins nothing, and five later `ref` changes in repo-E's settings did not re-fetch the checkout (VERIFIED observation; that `ref` is never compared is BELIEVED).
- **The version string lies.** Today's two project install records on this machine say 0.1.9 and 0.1.7; neither commit is its tag's commit, and the "0.1.9" build (main at `0c0610e`) is in no release tag ([skew_installed.py](_scratch/long-running-drift/scripts/skew_installed.py), run 2026-10-19). On 2026-10-14 two `/reload-plugins` calls switched a repo-E session to the "0.1.7" build, an untagged commit after v0.1.7, while its skills stayed at 0.1.4 (F4; the mechanism is unexplained, gap G2). A comparison of version strings cannot see either case.
- **Detection failed for 162 h.** `doctor` has warned "installed V, pinned P" since v0.1.1, but as a warning with exit 0 and "all good"; repo-E ran it 15 times, all on its first day, and `uv run dev setup` 0 times after the pin moved (F5). The skew was found by this research round.
- **Replay.** A check inside the plugin's own SessionStart and SubagentStart hooks that compares the loaded `${CLAUDE_PLUGIN_ROOT}` with the pin would have printed at 10 of 10 repo-E session starts in the window, the first 1.35 h after the pin moved, with no network call (VERIFIED from F1's session list; 0 false positives BELIEVED, since equal content is silent by construction). L1 and repo-P cannot skew: their agents and hooks live in the repository, and a `directory` marketplace "loads its current source files at every session start" (F7).
- Technical-lag research measures the same quantity for package ecosystems and finds it grows over time (Zerouali et al., JSEP 2019, [A formal framework for measuring technical lag in component repositories — and its application to npm](https://doi.org/10.1002/smr.2157); Decan, Mens and Constantinou, ICSME 2018, [On the evolution of technical lag in the npm package dependency network](https://arxiv.org/abs/1806.01545); SOURCED abstracts). Update bots reduce lag when their noise is budgeted: 11.3% of projects abandoned Dependabot (He et al., TSE 2023, [Automating Dependency Updates in Practice: An Exploratory Study on GitHub Dependabot](https://arxiv.org/abs/2206.07230), SOURCED abstract).

## 11. Upstream platform and model drift (VERIFIED; SOURCED changelog)
- **Rate.** 155 Claude Code versions shipped in the six months from 2026-04-19, about 26 a month; 193 changelog bullets in that window begin with Removed, Changed, Deprecated, Renamed or Breaking and name a harness surface, about 1.25 per version (keyword classification, not hand-checked; [cc_cadence.py](_scratch/long-running-drift/scripts/cc_cadence.py)). This machine ran 18 versions in 44 days ([cc_versions.py](_scratch/long-running-drift/scripts/cc_versions.py)). Updates apply "on the next launch, never mid-session" ([prompt caching](https://code.claude.com/docs/en/prompt-caching), SOURCED), so a long lead session and a fresh worker can run different versions.
- **Changes that touched harness assumptions in 10 days, none seen to break anything** ([changelog](https://code.claude.com/docs/en/changelog) 2.1.295-2.1.304, SOURCED): plugin hook transport failures now fail closed (2.1.299), `updatedInput` keys are validated and unknown ones dropped (2.1.300), Read gained `allow_large` (2.1.296), and transcripts record system prompts (2.1.300), which changed the record shapes this round's own forensics had to parse.
- **Silent overrides and stale doc facts.** `subagentPromptCacheTtl` in settings outranks `cacheTtl` in agent frontmatter ([prompt caching](https://code.claude.com/docs/en/prompt-caching)), so the frontmatter value on 3 of 7 agents is dead config while both say 1h; `IMPORT_HOPS = 5` still stands against "a maximum depth of four hops" ([memory docs](https://code.claude.com/docs/en/memory); [#47](https://github.com/Marius-Juston/agent-harness/issues/47), §5 check 8). H's plugin validation is pinned to Claude Code 2.1.296, 8 releases behind the runtime.
- **Model drift without an edit.** Agent frontmatter names an alias, so the model behind each agent changed three times in the transcript window with no harness change, and one repo-E researcher fell back to an older model for 94 of its 145 turns without saying so in its hand-back ([cc_versions.py](_scratch/long-running-drift/scripts/cc_versions.py); the trigger is not in the record). Hosted-model behaviour can shift within months (Chen, Zaharia and Zou 2023, [How is ChatGPT's behavior changing over time?](https://arxiv.org/abs/2307.09009), SOURCED abstract; old models, mechanism only).
- **Detection.** Both stale doc facts above were found by research rounds, not checks. Pinning Claude Code would block about 0.4 fixes a day, some of which the harness needs (BELIEVED); recording the version and re-checking on change fits better.

## 12. Warning decay and the case against more machinery (VERIFIED; SOURCED outside; [r1-against](_scratch/long-running-drift/r1-against.md))
- **Standing warnings are not acted on.** repo-E's `board lint` count at session start rose 72 → 138 from 10-13 to 10-16 and never fell; "suite audit due" was shown 80 times and "consolidation review due" 62 times, with no commit recording either review ([against_lint_series.py](_scratch/long-running-drift/scripts/against_lint_series.py)). H's count rose from 90 to 134. In clinical decision support, the odds of accepting a reminder fell 30% per additional reminder per encounter and 10% per 5-point rise in the share of repeated reminders, while a newly deployed reminder showed no decline over time (Ancker et al. 2017, [Effects of workload, work complexity, and repeated alerts on alert fatigue in a clinical decision support system](https://doi.org/10.1186/s12911-017-0430-8), abstract; SOURCED); physicians in the top quartile of alerts seen responded less (adjusted OR 0.38, 95% CI 0.35-0.42; Murad et al. 2022, [Distinct components of alert fatigue in physicians’ responses to a noninterruptive clinical decision support alert](https://doi.org/10.1093/jamia/ocac191), JAMIA, abstract; SOURCED). No study found measures how coding agents treat repeated session-start warnings (BELIEVED absence).
- **Tokens are not the cost.** repo-E's whole orient output (796 words) costs about $0.05 a session at cache-read prices; a 20-word line about $0.02 over a 14-session window ([against_orient_cost.py](_scratch/long-running-drift/scripts/against_orient_cost.py); 1.33 tokens per word ASSUMED). The cost is attention, build effort and refusals: the 12 follow-ups #220 filed were still open 6 days later; L1 filed 11 drift tickets and built 1; L1's one freshness check refused 5 of 91 land runs, and the HANDOFF it forced grew 176 → 7,944 words in 10 days ([against_check_refusals.py](_scratch/long-running-drift/scripts/against_check_refusals.py), [against_prose_churn.py](_scratch/long-running-drift/scripts/against_prose_churn.py)).
- **Measured harm is small.** 25 transcript sentences in which an agent remarked on stale docs, memory or instructions coded to 13 real drift events: 10 cost nothing, 1 cost a failed start, and 2 (one event) a cleanup ticket ([against_drift_encounters.py](_scratch/long-running-drift/scripts/against_drift_encounters.py), [against_encounters_coded.csv](_scratch/long-running-drift/scripts/against_encounters_coded.csv), [against_tally.py](_scratch/long-running-drift/scripts/against_tally.py)). Survivorship makes this a lower bound.
- **Deletion and regeneration beat maintenance** where tried (L3's rewrite left one dangling reference, caught by a review agent in a day), and the platform ships a semantic auditor: `/doctor prompt-audit` looks for "references to files or commands that don't exist, and files that contradict each other" in instruction files and accepts a path ([memory docs](https://code.claude.com/docs/en/memory#audit-your-instruction-files), SOURCED; precision unpublished and unmeasured here).
- Contradiction resolved: the adversarial seat argued from the docs that memory reaches the lead only; §9 measured 91% of workers carrying it. That strengthens its conclusion (do not list entries again; the index is everywhere) and raises the stakes of scope and provenance.

## 14. Recommendation for this project
### 14.1 Long-running additions (#282), in build order (BELIEVED unless marked)
1. **Loaded-root skew check.** The plugin's SessionStart and SubagentStart hooks hash the loaded `${CLAUDE_PLUGIN_ROOT}` (excluding `.in_use`, `.orphaned_at`, `__pycache__`) and compare it with the digest the pinned devkit release records for its plugin; on mismatch they print one line naming both versions and the fix command. Compare content, never the version string (§8: both installed records here carry a string that is not their build). `uv run dev doctor` reports skew as a failure (exit 1), and `uv run dev setup` runs `claude plugin marketplace update` then `claude plugin update`. This does not need #163; #163 stays a separate copier fix.
2. **Probes before a redesign.** G1: does `CLAUDE_CODE_PLUGIN_DIRS` (or `--plugin-dir`) set from project settings load the plugin from the uv-installed package before startup and shadow the marketplace install? If yes, skew becomes impossible rather than detected. G2: reproduce the `/reload-plugins` switch of §8 on a scratch pair of projects and report it upstream if it reproduces.
3. **Memory at write time.** The lead guidance requires a `source:` line (owner message, issue, PR or page) and a `verified:` date in every entry, writes a rule that applies beyond the repository at user scope, deletes an entry in the change that promotes it, and rewrites rather than appends. Within the template's word budgets.
4. **[#233](https://github.com/Marius-Juston/agent-harness/issues/233) re-scoped to flagged entries only.** orient prints one line per entry whose `source:` names a closed issue or a deleted path, or whose `verified:` (else `modified`) is older than 14 days, and nothing else; HANDOFF live state stays as specified. Target: at least 0.5 precision on the 36 labelled entries once `source:` fields exist (today's prose-based pointer check: 0.29).
5. **Warnings only when new or rising.** orient and the gate remember the last count per warning kind per machine and print a warning only when it is new or its count rose; a "due" nag with no recorded action in 10 sessions is dropped or becomes a board item. Measure the action rate per printed warning before and after on one project.
6. **Advisory LLM sweep for specs, design docs and docstrings, never for maintained instruction files** (0.87 vs 0.22). Try `/doctor prompt-audit` with a path first (reuse before build); the default fix it proposes is delete or regenerate, not edit. Advisory until the held-out recall study (item 8) shows recall of at least 0.7 and precision of at least 0.7 on planted claims with two models.
7. **[#229](https://github.com/Marius-Juston/agent-harness/issues/229) stays a warning**, exempting research notes and spans marked as historical or negative references ("removed", "do not reintroduce"); it never fired on real drift in held-out data. Re-replay with #236 before any promotion.
8. **Held-out recall study** of the sweep: plant stale claims in copies of real specs, docstrings and instruction files at known lines, run two models with the frozen prompt three times each, report recall, precision and run-to-run variance (pre-registered split).
9. **Platform**: on a Claude Code version change, orient prints the changelog bullets that match harness keywords (warning) and the canary probes of #102 run once. Raise `cleanupPeriodDays` on harness machines so drift evidence outlives 30 days (180 is ASSUMED; disk only).

### 14.2 From #220 (unchanged unless marked)
1. **No ADR directory** in agent-harness or the template. Decisions go to a test or hook when code can check them, else to a row of `.devkit/decisions.toml` with a reason marker of 5 words or fewer. Seed the table with the 6 prose-only rules (D01, D05, D07, D08, D11, D12; [r2-mechanisms M1](_scratch/adr-drift/r2-mechanisms.md)). The check starts as a warning printed by the gate and by `uv run dev integrate`; it becomes a gate after the held-out replay.
2. **Hook** denying `curl`/`wget`/WebFetch to the five endpoint prefixes of check 9, with allow-list tests for article pages and Europe PMC full text and an override for work on `devkit/lit.py`. Its effect is measured with the re-run in [#174](https://github.com/Marius-Juston/agent-harness/issues/174): at most 1 run in 20 per agent type calls a literature API directly.
3. **Gate now** (0 FP in-sample, no fitted rules): check 2 in `uv run dev integrate` (refuse a merge deleting a path that an open issue other than its own owns) and as a `board lint` error.
4. **Generated now**: integrate writes the floor raise (0.95 x passed when below 0.90 x passed); `uv run dev pr --partial` copies the DONE WHEN checklist and integrate writes the ticks back by exact text; `uv run dev orient` prints the live state of each issue or PR that HANDOFF's In flight, Next and Waiting sections name. **Changed by #282**: orient prints flagged memory entries only, not every entry (§9, 14.1 item 4).
5. **Warnings**: check 1a in `check_dev_commands` and check 7 until promoted, check 1b (`.py`), and the `board lint` comment-decision warning. Drop 1c as a gate and 1d entirely. **Changed by #282**: 1a exempts research notes and negative references (14.1 item 7), and every warning follows the new-or-rising rule (14.1 item 5).
6. **Decision level** (advisory): an auditor or sweep step that checks notes against the decision table, and a table search in `board new` (#238).
7. **Sweeps**: a weekly lychee workflow in agent-harness, with the template's config changed to exclude `doi.org` (cite-check already resolves DOIs) and keep the job token for GitHub; and a quote-presence sweep for doc URLs cited in code.
8. **Promotion rule**: a warning becomes a gate only after 30 held-out merges per repository with 0 FP; a gate that produces one FP drops back to a warning.

What would change this: a measured re-litigation rate of owner-policy decisions above about 1 in 10 decision-touching runs; owner decisions with rejected alternatives that agents keep re-proposing despite a table row (then add a short ADR body behind `why`); a Claude Code change that loads path rules on Bash writes and Grep; G1 succeeding (then the skew check guards only the fallback path); or a stale memory entry shown to steer work (then the model sweep moves from on-demand to weekly).

## 15. Limits
- One rater for every coding (decisions, reversals, mechanism calls, flags, memory labels, prose episodes, sweep verdicts); no inter-rater agreement. Three memory labels changed after reading the model's output, which biases the adjudicated sweep scores upward.
- H's history is 3 days and 69 merges for #220 and 8 days for #282; only L3, and L1 for a few weeks, give months of active history.
- Transcripts, memory and the probes come from one machine. Months-scale memory drift is unobservable here: transcripts are kept 30 days and no entry is older than 23 days. L3's main contributor works on another machine.
- The LLM sweep ran once, with one model and one prompt; its recall beyond 9 known claims is unknown. The memory sweep likewise.
- The changelog keyword count is unchecked by hand; the platform findings cover 10 days of changelog in detail.
- Kitayama, Kerbel, Buchgeher and Ahmeti are abstract-only; their per-condition run counts are unverified. Most #282 literature was read as abstracts or single tables.
- The URL re-check could not judge 26 URLs (bot walls, TLS failures from this machine).
- The research-auditor pass on the #282 sections is pending at the time of writing.
