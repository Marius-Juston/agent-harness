# r1: prior art and free tools for doc-code consistency, and the case against "add ADRs" and "add more drift checks"

Round 1 sub-question of #220. Search coverage: `dev lit status` 2026-10-13: openalex, crossref, europepmc, arxiv up; s2 down (HTTP 429, skipped on every query). Plus arxiv MCP (section reads), WebSearch, context7 (import-linter), GitHub and PyPI APIs.
Arithmetic: `drift_math.py` in this session's scratchpad (not committed; the inputs are the numbers quoted below and it only divides). Its outputs are marked VERIFIED (arith).

## Findings

### F1. Automated semantic doc-drift detectors sit at 57-75 % precision. That fails Google's bar for a blocking check (0 effective false positives) and its bar for a review comment (under 10 %).
- SOURCED: the best measured detector is [READU](https://arxiv.org/abs/2607.15780) (Baek, Krampf, Pradel, arXiv 2026, DeepSeek V4 Flash, high reasoning). It found README bugs just-in-time over 6,000 commits of six repositories: 244 TP, 81 FP, **75 % precision**, under $0.01 and under a minute per commit. Per-repository precision ran from 71 % to 82 %, except React at 21 %. Without its LLM alert judge, precision is 60 %. Single-LLM, mini-SWE-agent and Codex Review baselines got 58-63 %. DOCER, the rule-based deleted-reference detector, got 0 TP and 3 FP. A rule-based README updater got 19 % (Table II).
- VERIFIED (arith): 81/6000 = **1.35 false alerts per 100 commits** for READU, and 3.0 without the judge. At READU's rates, this repository's 252 commits (2026-10-11 to 10-13) would produce about 3.4 false and 10 true alerts. Recall is unknown, because READU reports no ground truth for missed bugs.
- SOURCED: on code comments, [C4RLLaMA](https://doi.org/10.1109/icse55347.2025.00035) (ICSE 2025, fine-tuned CodeLlama) corrects 65.0 % of just-in-time cases and 55.9 % of post-hoc cases (manual evaluation). [DocChecker](https://aclanthology.org/2024.eacl-demo.20.pdf) (EACL demo 2024) reaches 72.3 % accuracy on inconsistency detection. Both are benchmark numbers on comment/code pairs, not repository prose.
- SOURCED: the [configuration-smells study](https://arxiv.org/abs/2606.15828) (SCAM 2026, 100 repositories) measured heuristic precision. Syntactic smells are precise: Lint Leakage 58/62 (93.5 %) and Blind Reference 14/16 (87.5 %). The semantic smell, Conflicting Instructions, is not: 16/28 (**57 %**). Skill Leakage is 29/35 (83 %; the paper's text says 86 %, which does not match its own counts).
- SOURCED: [Sadowski et al., CACM 2018](https://6826.csail.mit.edu/2020/papers/google-analysis-cacm.pdf). A compiler (blocking) check at Google must produce "no effective false positives (the analysis should never stop the build for correct code)". Code-review checks may have "up to 10% effective false positives". Tricorder disables an analyzer whose "Not useful" ratio goes above 10 %.
- BELIEVED: deterministic checks qualify as gates: link and anchor checks, `dev` command names, frontmatter, generated diffs. The harness already runs these ([agent-harness.md §3](../../agent-harness.md#3-drift-verified-in-repository-a-sourced)). LLM drift judges qualify, at best, as advisory comments or sweep inputs. The 25 % false share comes on top of model drift over time, so a judge's precision must be re-measured whenever the model changes.

### F2. For agents, a false positive is not just noise. It is a work order.
- SOURCED: in [Sadowski et al.](https://6826.csail.mit.edu/2020/papers/google-analysis-cacm.pdf), humans who doubt a warning ignore it. The paper counts an issue as an "effective false positive" when developers take no action.
- BELIEVED: an agent told "the gate failed" acts on the warning. On a false alert, that action is editing correct prose to satisfy the checker, adding an exemption, or weakening the check. That is the gaming pattern already documented in [agent-harness.md §4](../../agent-harness.md#4-gaming-and-integrity-sourced-verified-in-repository-a). So a 25 % false share costs more in an agent repository than the Google figures suggest. ASSUMED: no study measures agents' responses to false-positive doc checks. This is a gap (G3).

### F3. Rule-based "reference still exists" checks are cheap and precise only in narrow scope.
- SOURCED: Tan, Wagner, Treude (EMSE 2023), [Detecting Outdated Code Element References in Software Repository Documentation](https://arxiv.org/abs/2212.01479) (DOCER) analysed over 3,000 GitHub projects. Most had at least one outdated code-element reference at some point. Of 15 projects sent issues, 4 confirmed and 4 called them false positives. Of 19 reported references, 5 were fixed. Changelogs and still-relevant user notes are named as false positives "difficult to eliminate".
- BELIEVED: the harness's backticked-path check (`check_links` in `devkit/checks.py`) is the precise subset of DOCER: a path either resolves or does not. Extending it to identifiers (constants, CLI options) brings in DOCER's false-positive classes: changelogs, historical notes, and research notes that cite a superseded value on purpose (for example "R0 (PR #171 first build)").

### F4. Many drift classes have no triggering commit, so a diff-time gate cannot see them, and a sweep is the only detector.
- SOURCED: in READU, 63 of 244 true README bugs (VERIFIED arith: 26 %) were "incorrect external references" (dead URLs, package names, platform requirements). Those can go stale with no commit in the repository. 32 of its 81 false positives (39 %) were "pre-existing issues" that the just-in-time judge rejects ([READU §I-J](https://arxiv.org/abs/2607.15780)). A just-in-time detector is blind to the backlog by design.
- SOURCED: at Google, a nightly FindBugs dashboard "saw little use because a bug dashboard was outside the developers' usual workflow". A 2009 Fixit week turned 44 % of reviewed issues into bug reports, but "manually triaging issues and filing bug reports is not sustainable" ([Sadowski et al.](https://6826.csail.mit.edu/2020/papers/google-analysis-cacm.pdf)). The pattern that worked was a one-off sweep that fixes every existing instance (ClangMR/Rosie; 57 % of patch recipients happy, 2 % negative), then a blocking check against new instances.
- VERIFIED (read `template/.github/workflows/maintenance.yml`): the template already uses the right shape for one class. A weekly lychee run keeps a single "Broken links" issue current and closes it when clean. The findings land on the board, which is the agents' workflow, not on a dashboard.
- BELIEVED: sweep beats gate when (a) the source of truth changes outside the repository (external URLs, model behaviour, upstream CLIs, the board), (b) the check is semantic and noisy (F1), or (c) staleness grows with time, not with a diff (DONE WHEN versus reality, HANDOFF and memory). Gate beats sweep when the check is deterministic, the fact is in the diff, and a fix is mechanical.

### F5. ADRs in open source are rarely kept up. The evidence that they help is about humans, not agents.
- SOURCED: in Buchgeher et al. (IEEE Access 2023), [Using Architecture Decision Records in Open Source Projects—An MSR Study on GitHub](https://doi.org/10.1109/access.2023.3287654) (MSR study of GitHub), ADR adoption "is still low", and about 50 % of repositories with ADRs hold only 1-5 ("tried but not yet definitively adopted"). Systematic use is a team activity over a long period, which a solo owner plus agents is not.
- SOURCED: [Nygard 2011](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions) asks for records of "one or two pages", kept "in the project repository", and a reversed decision kept but "marked as superseded". The stated benefit is avoiding "blind acceptance or blind reversal".
- SOURCED: Su et al. (ICSA 2026), [Evaluating Large Language Models for Detecting Architectural Decision Violations](https://arxiv.org/abs/2602.07609) checked 980 ADRs from 109 repositories for violations with open models. Accuracy is 0.83-0.91 and macro-F1 0.80-0.88, but most cases are "Compliant". Every model is weakest on "Code is Insufficient to Answer" (F1 0.71-0.79): "organizational, process-related, or cost-driven decisions". The examples in #220 are process decisions of exactly that kind: the #176 harm rule, #196's F0-only scope, CLI-not-MCP.
- VERIFIED (git log of project B's `docs/adr/`): its 5 ADRs (1,966 words) were all written on 2026-10-11 with 1-3 commits each, none superseded. No `.py` or `.toml` file in project B references them, so no check enforces them. Two days of history cannot show decay either way.

### F6. Every new doc layer is another place to drift, and agent context files already decay in a measured way.
- SOURCED: [Chakrabarti, arXiv 2026](https://arxiv.org/abs/2608.11095) studied 247,694 instruction lifetimes in 1,867 repositories. Agent prompts grow +226 % over their lifetime. The deletion hazard *falls* with an instruction's age (log-hazard −0.032 per commit, 95 % CI [−0.047, −0.019]), which the author reads as lost rationale, against the rival account of rising staleness. Stale instructions accumulate instead of being pruned. One discrepancy: the abstract says "+4.9 net instructions every commit", while Fig. 4 says 4.9 % per commit after a rewrite. Use the CI'd hazard, not the 4.9.
- SOURCED, and evidence *for* recording rationale: in the same paper, comments carrying an instruction's reasoning removed 99.3 % of excess instructions, but in synthetic IFEval-inverted worlds, not real repositories. That is the strongest argument for a "why" record, and it is untested on agents in the field.
- SOURCED: [Agent READMEs: An Empirical Study of Context Files for Agentic Coding](https://doi.org/10.1145/3840295) (TOSEM 2026) (2,303 context files) finds that these files "evolve like configuration code through frequent, small additions". [Configuration smells](https://arxiv.org/abs/2606.15828) finds Context Bloat in 42 % of 100 files.
- SOURCED: when a skill body loads only on demand, [Agent Skill Evolution, arXiv 2026](https://arxiv.org/abs/2610.04832) found agents keep about 51 % of the action gain of a rule (+0.23 on average when loaded). The gain comes mainly from rules "that name a command or path". BELIEVED, by extension: an ADR directory read on demand delivers about half the effect of a one-line rule, and a narrative ADR delivers less than a rule naming a command.
- SOURCED, via the existing note: context files add over 20 % inference cost, and overviews do not help ([agent-harness.md §1](../../agent-harness.md#1-what-guidance-helps-sourced)).
- VERIFIED (`measured_words()`): this repository's CLAUDE.md costs 277 words against a 600 budget. Non-scratch `docs/**/*.md` totals 36,769 words (`wc -w`). An ADR index loaded each session spends always-loaded budget. ADR bodies on demand add to the 36.8k words that link and cite checks must walk.

### F7. The one drift in #220 traced here was a write-time race, not decay, and the existing rule "link, do not copy" covers it.
- VERIFIED (git): `986e764` shipped R4 at 09:42:21. The note `49ed040`, committed at 09:50:50, still described "PR #171 as built" with R0. The fix `3635292` came at 09:57:26. The stale text lived about 6.5 minutes and was caught by the lead. The note had copied a fact about another PR's state instead of linking the commit.
- BELIEVED: a constant-versus-prose gate would have needed the note to restate the constant in machine-readable form. That is the copying the project rule ("Facts live in one place. Link to them") already forbids. Single-source generation, a link, or `cog` beats a consistency check here.

## The case against, and what would change each conclusion

**Against "add ADRs" (BELIEVED, from F5, F6, F7):**
- An ADR duplicates what the gate, CLAUDE.md and research notes already hold, so it is another place to drift.
- Agents load it on demand, which keeps about half the effect at best. Narrative helps less than a rule naming a command.
- Open-source practice shows ADR sets abandoned after 1-5 records.
- The decisions most at risk (process and scope) are the ones no checker, LLM or rule-based, can verify against code.

The cheaper alternative: put each binding decision as one rule line where agents already look (CLAUDE.md, an agent file, a skill), with a link to its evidence (the research note, the issue). Encode it as a check when it is code-inferable (import-linter, a `dev` check). Keep supersession by editing the rule and the note's Status line.
- *Would change:* (a) a measured re-litigation rate: sessions that reopen a decided question, counted from transcripts with `dev agent-stats`, above about 1 in 10 decision-touching runs, and falling once an ADR exists. (b) Evidence that agents given a `supersedes` chain revert removed layers less often than agents given a rule plus a link. (c) The rationale-comment result of [Chakrabarti](https://arxiv.org/abs/2608.11095) replicated on agents in real repositories. That would argue for a short "why" beside each rule, not necessarily for an ADR directory.

**Against "add more drift checks" (BELIEVED, from F1-F4, F7):**
- Each new semantic gate at 57-75 % precision turns into agent work orders on correct text, and into pressure to add exemptions.
- Diff-time gates cannot see external or time-based drift.
- The one drift traced here (F7) was a breach of the existing single-source rule, which a generator or a link fixes better than a checker.

Prefer, in order: (1) single-source generation, with `cog --check` or `dev docs` diffs; (2) deterministic gates only (0 FP, Google's compiler bar); (3) a weekly sweep that keeps one board issue per drift class, the `maintenance.yml` pattern, for external, semantic and time-based drift; (4) an LLM judge only as a sweep input, re-measured per model.
- *Would change:* (a) a semantic detector measured on this repository's own history with precision at or above 90 % and a stable rate across a model change: then it can become a review comment. At 100 % on a held-out set it can become a gate. (b) Evidence that agents handle a false alert by flagging it rather than editing prose or the check, say over 90 % of trials in a micro-eval, which would lower the cost in F2. (c) Drift classes that recur in diffs at a rate where a sweep's lag (up to 7 days) costs more than gate noise.

## Gaps seen, not closed
- G1. No study measures documentation decay rates in agent-written repositories directly, apart from context files (F6) and PR description/code mismatch (1.7 % of 23,247 agentic PRs; Gong et al. (MSR 2026), [Analyzing Message-Code Inconsistency in AI Coding Agent-Authored Pull Requests](https://doi.org/10.1145/3793302.3793583), abstract only).
- G2. Ahmeti et al. (2024), [Architecture Decision Records in Practice: An Action Research Study](https://doi.org/10.1007/978-3-031-70797-1_22), the ADR action research: abstract not available through OpenAlex, and the publisher page redirected to login. Not read. Buchgeher's full text could not be fetched (IEEE returned HTML), so only the abstract's numbers are used.
- G3. No source on how coding agents react to false-positive doc checks (F2). This needs a micro-eval: plant a correct note, a false alert, and three trials.
- G4. READU's recall is unmeasured, its prompts are in an artifact I did not open, and its model cost and provider terms for this use were not checked.
- G5. The repository history is 3 days old (252 commits), too short to measure false-positive rates of the existing gate checks. Only 6 commits touch `devkit/checks.py`. Commits whose messages mention skips or exemptions: `fdb60c0` and `313647e` (skip research README and scratch).
