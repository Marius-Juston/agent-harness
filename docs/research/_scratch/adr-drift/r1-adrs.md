# r1: ADRs for an agent-run repository (#220)

Search coverage: `dev lit status` 2026-10-13: openalex ok (key), crossref ok, europepmc ok, arxiv ok, s2 DOWN (rate limited, no key), so discovery was "OK, partial". I also used the arxiv MCP, WebSearch and WebFetch. Four full texts were refused with HTTP 403/418 (IEEE Access, TechRxiv, ACM DL, Medium), so those papers are abstract-only below. S2's citation graph was not used.

## Answer
**Yes, but a minimal version.** The harness and its template should ship ADRs. Use Nygard's three-part body with MADR's `status` front matter, plus two fields that agents need: `evidence:` (a research note) and `enforced-by:` (a path and a literal marker). The gate checks mechanical facts only: the status vocabulary, numbering, two-way supersession links, the markers, that no accepted ADR is edited in place, and that each accepted ADR is referenced from somewhere. The reasons are below. In this repository 5 of 23 comment-born decisions live only in GitHub comments, 6 changed an issue's scope without editing its DONE WHEN, and one recorded rule was silently deleted for word budget and restored 8 hours later. The agent-specific evidence that a decision record changes behaviour is real but weak: preprints, one vendor study, one model family, and one pre-registered study whose frontier effect does not survive correction.

### F3. Empirical SE evidence on ADR adoption and use (SOURCED)
- **Adoption is low and often abandoned early.** Buchgeher et al. ran a mining study of GitHub repositories with ADRs: adoption "is still low" but rising each year; "about 50% of all repositories with ADRs contain just one to five ADRs", that is, tried but not adopted; systematic use is "a team activity conducted by two or more users over a longer period"; most use Nygard's template ([Using Architecture Decision Records in Open Source Projects—An MSR Study on GitHub](https://doi.org/10.1109/access.2023.3287654), IEEE Access 2023; abstract only, so the repository counts were not fetched).
- **Agent-active repositories almost never carry decision records.** Díaz et al. sampled 5,435 repositories from the 116,211 in AIDev. They detected ADR and decision-log directories (`docs/adr/**`, `docs/decisions/**`, `.specify/memory/**`) at about 1% in each visibility band (intervals G1 [0.5–1.8], G2 [0.5–1.9], G3 [0.2–1.4]), with no gradient by visibility. Rule files together with ADRs co-occur in 66 of 5,435. The authors note that decision memory kept in external tools leaves no trace in git ([Methodological Harness in Agentic Software Engineering: An Empirical Study on Mining Software Repositories](https://arxiv.org/abs/2609.32014), 2026 preprint, §4.2).
- **Rationale and alternatives are what ADRs most often leave out.** Miccio Palermo et al. analysed 4,316 ADRs from 547 projects. ADRs mostly record existence, technology and process decisions, while "alternatives, decisions drivers, and some quality concerns remain under-documented", with recurring mismatches against MADR's sections ([A Text Mining and Classification Approach for Analyzing Architecture Decision Records](https://arxiv.org/abs/2609.07375), 2026 preprint).
- **An industrial action-research study helped with culture but not with distributed components.** Ahmeti et al. ran 7 interviews, then a 3-month ADR introduction in one microservice company. ADRs addressed documentation culture, knowledge transfer and what to document. Distributed-systems challenges "remain open", and "the decision on where documentation is stored has a massive influence on its perceived usefulness" ([Architecture Decision Records in Practice: An Action Research Study](https://research.chalmers.se/en/publication/542849), ECSA 2024, LNCS 14889; abstract only).
- **On format, Nygard beat MADR on comprehension in a student experiment.** Nogueira et al. screened Tyree/Akerman, Nygard, arc42, Y-statements and MADR with DESMET; Nygard and MADR came top. In a controlled experiment with undergraduates, Nygard "outperformed MADR in terms of the Overall Score". Nygard supports concise documentation, and MADR supports structural detail ([One Size Fits All? An Empirical Comparison of ADR Templates regarding Comprehension, Usability, and Ease of Adoption](https://arxiv.org/abs/2604.27333), 2026 preprint; N not in the abstract).
- **Decay and re-litigation have no measured rate.** I found no study that measures how often recorded decisions are reversed, ignored or re-argued (searches: "architectural decision reversal revisiting decisions empirical", "architecture decision records sustainability evolution superseded"). Nygard's argument against "blind acceptance or blind reversal" is reasoning, not data ([Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)).

### F4. Agent-specific evidence (SOURCED; all 2026 and model-dated; none replicated)
- **Recorded rationale beat the instruction alone (one preprint).** Kitayama built sqlew, which serves ADRs to Claude Code over MCP, and compared no ADR, ADRs from the start, and ADRs added retroactively on one 12.5-turn TypeScript build. With ADRs, time fell 10.1% (496 vs 552 min) and tool calls fell 10.8%. With the same TDD rule in CLAUDE.md, the ADR conditions wrote 16-25 E2E tests and the vanilla condition wrote 0. The author concludes that models comply more with "why" than with "what" ([Rediscovering Architectural Decision Records: How Persistent Design Context Improves LLM Code Generation](https://doi.org/10.36227/techrxiv.177205025.54351571/v1), TechRxiv preprint). Limits: the author also wrote the tool; one project; the abstract implies one session per condition (BELIEVED, because the full text was refused); there is no statistical test.
- **Decision retrieval raised compliance on decisions that are invisible in code (vendor study).** Claude Code with codebase access only versus the same agent with Brief, a product-context retrieval tool that includes recorded decisions: decision compliance was 95% versus 46% over 8 tasks and 41 weighted decision points. The baseline scored 100% on decisions visible in code and 0-33% on decisions that need outside context ([Context-Augmented Code Generation: How Product Context Improves AI Coding Agent Decision Compliance by 49%](https://arxiv.org/abs/2605.08112)). In the authors' own words, the decisions "were designed by the authors" to be invisible, and with no "inspect all ADRs" baseline the paper "cannot attribute the full improvement" to retrieval rather than to planning. The study covers one repository and only Claude (§7.6).
- **The pre-registered study helps weaker readers, and its frontier effect was not confirmed.** Kerbel et al. versioned a `context.md` that records "the decisions taken, the alternatives rejected", which agents may write only under human review, and pre-registered an experiment on SWE-bench Verified. A small local executor gained +26 pp localization from context written by a stronger model and +0.0 pp from context it wrote itself. A frontier agent gained +14.6 pp resolve on constraint-sharing tasks (p = 0.041 uncorrected, 0.081 after Holm, so the authors report only the direction) with 32% fewer tokens per resolved task. Exploratorily, a sharded store that the agent read selectively beat a monolith at a third of the tokens. On a broad random sample, the frontier agent sat at a ceiling that no context raised ([Context Inheritance: A Git-Native Architecture and Pre-registered Study of Repository Context for AI Coding Agents](https://doi.org/10.1145/3843282.3844425), abstract only).
- **A contrary result: context files do not move correctness.** Over 288 runs on two frontier agents (Claude Code, Codex) and 17 real tasks, the context strategy did not measurably change correctness, bounded to ≤10-15 pp by equivalence testing. Agents failed on implementation skill, not on missing repository knowledge ([Do Context Files Help Coding Agents? A Two-Agent Ablation Study on Real Repositories](https://arxiv.org/abs/2607.27250)). This agrees with the prior already in [agent-harness.md](../../agent-harness.md) §1: context files do not raise success, they cost more than 20% more inference, and non-standard practices are the part that helps.
- **Agents make architectural decisions implicitly.** Konrad et al. call this "vibe architecting" and propose review practices and decision records to govern it. That is a position paper with an illustrative demonstration, not an outcome study ([Architecture Without Architects: How AI Coding Agents Shape Software Architecture](https://doi.org/10.1109/icsa-c68850.2026.00087), ICSA-C 2026).
- **Synthesis (BELIEVED).** The benefit concentrates on decisions an agent cannot infer from the code: owner policy, rejected alternatives, and the reason a rule exists. That matches F1, because every lost or drifted item there is of that kind. None of these studies measures re-litigation across sessions directly. The size of any benefit is unknown for this harness's model (Opus 5.5).

### F5. Formats (SOURCED)
- **Nygard (2011).** Title, Context, Decision, Status, Consequences. Status starts as "proposed" or "accepted", and later ADRs mark older ones "deprecated" or "superseded" with a reference. "ADRs will be numbered sequentially and monotonically. Numbers will not be reused." A significant decision is one that affects "the structure, non-functional characteristics, dependencies, interfaces, or construction techniques" ([Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)).
- **MADR 4.** Optional YAML front matter: `status: "{proposed | rejected | accepted | deprecated | … | superseded by ADR-0123}"`, `date`, `decision-makers`, `consulted`, `informed`. Its sections are Context and Problem Statement, Decision Drivers, Considered Options, Decision Outcome and Consequences ([MADR adr-template.md](https://github.com/adr/madr/blob/develop/template/adr-template.md)).
- **Y-statements.** "In the context of …, facing …, we decided for …, to achieve …, accepting that …", from Zimmermann's SATURN 2012 talk and building on Fairbanks' Architecture Haikus ([Design Practice Repository: ADR Y-form](https://socadk.github.io/design-practice-repository/artifact-templates/DPR-ArchitecturalDecisionRecordYForm.html)). It is one sentence, which suits an always-loaded index line (BELIEVED).

## Recommendation for #220 (BELIEVED unless marked)
1. **Ship ADRs, kept small.** Add `docs/adr/` to the template and this repository, with a generated index of one line per ADR (number, status, a Y-statement summary) in `docs/generated/`. CLAUDE.md/HARNESS links the index, not each ADR. This keeps the context budget, and Kerbel's exploratory result favours a selectively read, sharded store over a monolith.
2. **Format.** Use Nygard's body (Context, Decision, Consequences), which is the shortest, did best on comprehension (F3) and is the commonest. Add front matter: `status` (proposed | accepted | deprecated | superseded by ADR-NNNN), `date`, `decided-by` (owner or lead), `evidence` (a path to a research note, required for accepted), `supersedes`, and `enforced-by` (a list of `path: "literal"`). Number monotonically and never reuse a number.
3. **When one is required.** An ADR is required for each of the following:
   - (a) an owner directive that binds beyond one issue (licence, privacy, scope; for example #37 or #9's privacy rule);
   - (b) a lead decision that picks among researched options, overrides a note's recommendation, or narrows or widens an issue's DONE WHEN (#196, #84);
   - (c) removing or reversing a recorded rule (C1, C2);
   - (d) a gate or harness policy that a worker could reasonably "fix" away (for example, board lint findings are warnings, not failures, which today is only a docstring in `devkit/board.py`).

   Local trade-offs inside one function stay as code comments, which is already true for 9 of the 18 recorded decisions here.
4. **Supersede, never amend in place.** An accepted ADR may change only its `status` line and back-links. The new ADR has `supersedes:` and the old one gets `superseded by`. Project B's in-place amendment becomes a new ADR.
5. **Gate checks.** All of these are deterministic and offline; they report how many ADRs they examined, and zero fails per `ran.py`:
   - **a. Status vocabulary.** `status` is in the vocabulary; `date` is ISO; numbers are unique and contiguous.
   - **b. Supersession links.** `superseded by N` ⇔ N's `supersedes` names this ADR, and both files exist.
   - **c. Enforced-by markers.** Every `enforced-by` literal is present in its path. This catches C1, the rule deleted to fit a word budget (VERIFIED that the marker vanished at `4d61af0`). A word-budget trim that must remove the text then has to supersede the ADR, which makes the reversal explicit.
   - **d. No in-place edits.** The diff against the merge base shows no edit to an accepted ADR's body (for example `## Decision`) beyond the status and link lines; the override is a new ADR.
   - **e. References (warning only).** Each accepted ADR is referenced by at least one non-ADR, non-scratch file. Project B's harness ADR would warn: 0 such references.
   - **f. Evidence link resolves.** An accepted ADR's `evidence` path resolves; the existing link check covers this.
6. **Comment-born decisions.**
   - **Lead skill and board lint:** a lead or owner comment that changes scope must edit the issue's DONE WHEN, which fixes the 6 of 23 cases. `board lint` could warn when the newest owner or lead comment is newer than the last body edit and contains "DONE WHEN" or "decision".
   - **Promotion:** a decision that binds beyond its issue is promoted to an ADR in the PR that implements it.
7. **How agents obey.**
   - **Discovery:** agents find ADRs through the index, the `enforced-by` anchors (a comment `ADR-NNNN` beside the marker, so `git grep ADR-` from the code finds the reason), and `dev board brief`, which could list ADRs whose `enforced-by` paths overlap the issue's Owns.
   - **Rationale:** Kitayama's "why beats what" (F4, weak) argues for keeping the Context paragraph short but present.

## Gaps seen, not closed
- There is no empirical rate of decision reversal or re-litigation, for human teams or agents. A measurement plan: count reverted rules in this repository and project B over 3 months, before and after ADRs (an issue candidate).
- Kitayama, Kerbel, Buchgeher and Ahmeti are abstract-only here (403/418). The run counts per condition and Buchgeher's repository counts are unverified.
- No study compares an ADR index against CLAUDE.md rules head to head on one model. A small `dev eval` would be cheap to run: plant an owner decision as an ADR versus as a CLAUDE.md line versus only in an issue comment, and measure reversal by a builder in a later session.
- The coding of the 23 decisions has one rater. A second rater on the 106 comments would give agreement.
- The 23 owner-directive issues are counted by a Context-section regex; directives phrased in any other way are missed.
