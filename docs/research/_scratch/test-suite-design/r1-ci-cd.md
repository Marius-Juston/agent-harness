# r1: CI/CD evidence and practice for test suites

Search coverage: `uv run dev lit status` on 2026-10-12 showed openalex, crossref, europepmc and arxiv up and s2 down (rate limited, shared pool). Every search ran with s2 skipped. The skip matters little here, because the core CI papers turned up through openalex or crossref. Also used: the arxiv MCP (two papers, sections only), WebFetch of official docs (DORA, GitHub, pytest, testmon, Google SWE book, Fowler), the GitHub and PyPI APIs, and `gh` against this repo, repo-E and repo-L.

## Findings

### F1. DORA: what the research ties to CI and test automation
- **10-minute feedback budget (SOURCED).** DORA's test-automation capability: "Developers should be able to get feedback from automated tests in less than ten minutes", both locally and in CI ([DORA: test automation](https://dora.dev/capabilities/test-automation/)). The CI capability: tests "should not take more than a few minutes to run, with an upper limit of about 10 minutes" ([DORA: continuous integration](https://dora.dev/capabilities/continuous-integration/)).
- **What predicts performance (SOURCED).** Three things: developers "primarily responsible for creating and maintaining suites of automated tests"; trunk-based development with merges into trunk at least daily (2015 State of DevOps Report); and "An agreement that when the build breaks, fixing it should take priority over any other work" ([DORA: test automation](https://dora.dev/capabilities/test-automation/), [DORA: CI](https://dora.dev/capabilities/continuous-integration/)). These pages give no effect sizes. The underlying data are DORA's self-reported surveys, not experiments (BELIEVED, from the method of the State of DevOps reports in general).
- **Reliability over size (SOURCED).** "A test suite of ten tests that is reliable, fast, and trustworthy is much better than" a large untrusted one. Flaky tests are not to be tolerated. A sign of an unhealthy suite is when one change forces updates to many unit tests ([DORA: test automation](https://dora.dev/capabilities/test-automation/)). The page's suggested measures: the share of commits that trigger tests with no manual step, the time from a build breaking to its fix, and "Test failures always indicate a real defect" ([DORA: CI](https://dora.dev/capabilities/continuous-integration/), [DORA: test automation](https://dora.dev/capabilities/test-automation/)).
- **AI-assisted development (SOURCED, weakly specified).** DORA 2024 found that AI adoption raises individual productivity, but "it also negatively impacts software delivery stability and throughput". The report reminds teams that "fundamentals like small batch sizes and robust testing remain crucial" ([DORA 2024 report page](https://dora.dev/research/2024/dora-report/)). InfoQ reports "a drop in throughput (1.5%) and stability (7.2%) for environments where AI had been adopted", from "a global survey of over 39,000 professionals" ([InfoQ, 2024-11](https://www.infoq.com/news/2024/11/2024-dora-report/)). Other coverage frames these as per 25% increase in AI adoption. I did not read the report PDF, so the exact scale of the effect is unverified. DORA 2025 calls AI "an amplifier, magnifying an organization's existing strengths and weaknesses" ([DORA 2025 report page](https://dora.dev/research/2025/dora-report/)). For an agent-run repo, the gate is the strength that AI amplifies (BELIEVED).

### F2. Pipeline staging: a fast commit stage, slower stages later
- **Commit stage (SOURCED).** Fowler: "the XP guideline of a ten minute build is perfectly within reason". "The commit build is the one that has to be done quickly". The second stage "runs a different suite of tests that do hit a real database and involve more end-to-end behavior". It "may not run after every commit" ([Fowler, Continuous Integration, updated 2024-01-18](https://martinfowler.com/articles/continuousIntegration.html)).
- **Google presubmit and post-submit (SOURCED).** Presubmit runs "only fast, reliable ones". Post-submit can "accept longer times and some instability, as long as you have proper mechanisms to deal with it". Most teams run small (unit) tests in presubmit. TAP handles more than 50,000 changes a day and about four billion test cases a day. It batches changes, then splits a failing batch and reruns it to find the culprit ([Software Engineering at Google, ch. 23](https://abseil.io/resources/swe-book/html/ch23.html)).
- **The research version of the same split (SOURCED).** An FSE 2014 study runs regression test selection in a pre-submit phase and test-case prioritization in a post-submit phase, so that failures are reported sooner ([Techniques for improving regression testing in continuous integration development environments](https://doi.org/10.1145/2635868.2635910) (FSE 2014)).
- **Implication (BELIEVED).** Three tiers fit. Per change: the full fast suite, kept under about 10 min wall time. Before merge: the same suite, re-run on the merged tree. Nightly or weekly: slow, live, soak and mutation work, which may be flaky and must be triaged rather than block merges.

### F3. Regression test selection (RTS) and test impact analysis
- **Dynamic, file-level RTS is safe and simple (SOURCED).** Ekstazi tracks which files each test touches at run time. On 615 revisions of 32 Java projects it cut end-to-end test time by 32% on average, and by 54% for longer-running suites ([Practical regression test selection with dynamic file dependencies](https://doi.org/10.1145/2771783.2771784) (ISSTA 2015)).
- **Static RTS is sometimes unsafe (SOURCED).** On 985 revisions of 22 projects, class-level static RTS matched Ekstazi's savings "but at the risk of being unsafe sometimes", while method-level static RTS "performs rather poorly" ([An extensive study of static regression test selection in modern software evolution](https://doi.org/10.1145/2950290.2950361) (FSE 2016); abstract read from the [authors' PDF](https://mir.cs.illinois.edu/~marinov/publications/LegunsenETAL16StaticRTS.pdf)).
- **Python, coverage-based RTS (SOURCED).** Measured against mutants, the selected set missed 0-2% of faults at file granularity but 16-24% at line granularity ([Regression Test Selection Tool for Python in Continuous Integration Process](https://doi.org/10.1109/saner50967.2021.00077) (SANER 2021)). The study covers three projects only, so N is small.
- **Meta predictive test selection (SOURCED).** A model learned from historical outcomes halved testing infrastructure cost while still reporting "over 95% of individual test failures and over 99.9% of faulty changes" ([Predictive Test Selection](https://arxiv.org/abs/1810.05286) (ICSE-SEIP 2019)). The motivation behind it: "almost 99.9% of test targets selected by build-dependency-based selection strategy pass". Picking only the two highest-scoring targets already caught at least one failure on 70% of faulty changes (§III-B and §V of the same paper). The approach needs a large history of test outcomes. Google likewise reports that "very few of our tests ever fail" and that failing tests are "closer" to the code they test ([Taming Google-scale continuous testing](https://doi.org/10.1109/icse-seip.2017.16) (ICSE-SEIP 2017)).
- **Cheap metadata-only techniques (SOURCED).** An ISSTA 2021 study pulls RTS and RTP that use only VCS and CI metadata into one methodology and evaluate it across heterogeneous projects ([Empirically evaluating readily available information for regression test optimization in continuous integration](https://doi.org/10.1145/3460319.3464834) (ISSTA 2021)). The abstract does not state the effect sizes.
- **Tools (SOURCED via API, 2026-10-12).**
  - [pytest-testmon](https://github.com/tarpas/pytest-testmon), MIT, 1,021 stars, last push 2025-12-01, PyPI 2.2.0. It records each test's dependencies with coverage.py as checksums of code blocks and stores them in `.testmondata`, independent of VCS. It does not track static data files or network services ([testmon.org](https://testmon.org/), [determining affected tests](https://testmon.org/blog/determining-affected-tests/)).
  - Launchable, CloudBees' predictive test selection since the August 2024 acquisition ([SiliconANGLE](https://siliconangle.com/2024/08/07/cloudbees-acquires-ai-based-software-testing-startup-launchable/)). The CLI repo now redirects to `cloudbees-oss/smart-tests-cli` (Apache-2.0, 27 stars). The service is commercial SaaS and its free tier is unconfirmed, so it does not fit a free, non-commercial project (BELIEVED).
- **This harness today (VERIFIED by reading `devkit/gate.py:235-255`).** `dev test --affected` is static, file-level selection. It selects changed test files plus test files that import a changed module by name. Transitive importers are missed, which is unsafe in the Legunsen sense. Any change to `pyproject.toml`, `uv.lock` or `tests/conftest*` falls back to all tests. The design is sound only because the gate (`dev check`) always runs the whole suite. Selection is a local iteration aid, never the gate (BELIEVED, consistent with the FSE 2014 pre-submit and post-submit split).

### F4. Merge queues and keeping main green
- **Why it matters (SOURCED).** Uber's SubmitQueue builds changes speculatively and lands only those that pass, so the mainline stays green ([Keeping Master Green at Scale](https://doi.org/10.1145/3302424.3303970) (EuroSys 2019)). Its 2025 successor cut CI resource use by about 53%, CPU by 44% and P95 wait by 37% ([CI at Scale: Lean, Green, and Fast](https://arxiv.org/abs/2501.03440) (ICSE-SEIP 2025)). The same paper notes that GitHub's merge queue and GitLab's merge trains only speculate along success paths, so a failure forces the changes behind it to retest (§II-B). A flaky test therefore costs a queue more than it costs a single PR (BELIEVED).
- **GitHub merge queue (SOURCED).** It is available on "all public repos owned by organizations" and on private and public repos on GitHub Enterprise Cloud ([GitHub changelog, 2023-07-12](https://github.blog/changelog/2023-07-12-pull-request-merge-queue-is-now-generally-available/)). The current docs page I fetched gives no availability statement, so whether this still holds is BELIEVED. Workflows must listen to `merge_group`, or their checks never run in the queue. A failing group's PR is removed and the queue rebuilds without it ([Managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)). The free alternative is strict required checks ("Require branches to be up to date before merging"), which makes the PR author update the branch ([About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)).
- **The sibling repos cannot use it (VERIFIED with `gh api`).** agent-harness is public but user-owned, and repo-E is private and user-owned, so neither is eligible under the rule above. `uv run dev integrate` already does a serial merge queue by hand: it re-gates the PR merged onto main in a throwaway worktree, then merges (`devkit/cli.py:140`). For a single-lead repo that is enough (BELIEVED).

### F5. Flaky tests: how common, why, and quarantine
- **Google, 2016 (SOURCED).** About 1.5% of all test runs report a flaky result. "Almost 16% of our tests have some level of flakiness". "About 84% of the transitions we observe from pass to fail involve a flaky test". The mitigations listed are: rerun failing tests; mark a test flaky so it fails only after 3 consecutive failures (which "encourages developers to ignore flakiness"); and auto-quarantine above a flakiness threshold, which "removes the test from the critical path and files a bug" but "could easily mask a real race condition" ([Micco, Google Testing Blog](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)).
- **Python specifically (SOURCED).** Across 22,352 PyPI projects and 876,186 tests, 7,571 tests were flaky. Order dependency caused 59%, test-infrastructure problems 28%, and the remaining 13% came mostly from network and randomness ([An Empirical Study of Flaky Tests in Python](https://doi.org/10.1109/icst49551.2021.00026) (ICST 2021)). Randomizing test order therefore targets the largest Python cause. pytest-randomly shuffles the order, resets `random.seed` and prints the seed, and `--randomly-seed=last` replays it ([pytest-randomly README](https://github.com/pytest-dev/pytest-randomly)).
- **Root causes, Java era (SOURCED).** An FSE 2014 study classified 201 flaky-test fix commits from 51 projects ([An empirical analysis of flaky tests](https://doi.org/10.1145/2635868.2635920) (FSE 2014)). A 2021 survey covers 76 papers ([A Survey of Flaky Tests](https://doi.org/10.1145/3476105) (TOSEM 2021)).
- **What developers say (SOURCED).** From 335 developers: developers worry less about the compute cost of reruns than about "the loss of trust in the test outcomes" ([A Survey on How Test Flakiness Affects Developers and What Support They Need To Address It](https://doi.org/10.1109/icst53961.2022.00020) (ICST 2022)). From 170 respondents and 38 StackOverflow threads: developers who see flaky tests more often may be more likely to ignore genuine failures ([Surveying the developer experience of flaky tests](https://doi.org/10.1145/3510457.3513037) (ICSE-SEIP 2022)).
- **This harness (VERIFIED from `pyproject.toml` and a run with pytest 9.1.1 on 2026-10-12).** It already uses pytest-randomly and pytest-xdist. But `addopts` contains `-p no:cacheprovider`. As a result `--randomly-seed=last` fails with "The cacheprovider plugin is required to use 'last'", as the [pytest-randomly README](https://github.com/pytest-dev/pytest-randomly) warns. `--lf` is still accepted, but it ran all 21 tests of `tests/test_security.py`: with no cache to read, it does nothing (BELIEVED; see the [pytest cache docs](https://docs.pytest.org/en/stable/how-to/cache.html)). A printed seed can still be replayed with `--randomly-seed=<n>`.
- **Quarantine tools (SOURCED via API).** [pytest-rerunfailures](https://github.com/pytest-dev/pytest-rerunfailures): MPL-2.0, 16.7 (2026-09-17), active. [pytest-timeout](https://github.com/pytest-dev/pytest-timeout): MIT, 2.4.0. Recommended policy (BELIEVED, from Google and DORA): no blanket reruns in the gate. A test found flaky gets a `flaky` marker that keeps it out of the gate, plus an issue with an owner and a deadline. A cap on the marker count, like the existing word-budget ratchets, stops quarantine from growing without limit.

### F6. Nightly versus per-PR
- **Evidence (SOURCED).** It is all practice, not experiment: Fowler's secondary build, Google's post-submit with batching and culprit finding, and the FSE 2014 post-submit prioritization (F2). I found no controlled study comparing defect escape under nightly and per-PR scheduling (gap).
- **This harness (VERIFIED from `devkit/gate.py:225-231,313` and `.github/workflows/ci.yml`).** CI runs `uv run dev check --no-cache` without `--full`, so tests marked `slow` (2 markers in `tests/`) never run in CI. The weekly `schedule` job runs only the security steps. Live tests run only for `tests/test_security.py`. A scheduled `--full` run would close that hole.
- **Sibling data (VERIFIED with `gh`, 2026-10-12).** repo-L, a private repo, has a daily `cron: '17 3 * * *'` soak (`timeout-minutes: 180`). It ran once, on 2026-09-26, and took 64 min. Its per-push `core` job took 7 min and then 39 min on the same day, and its `postgres` job failed on `docker create` on every push that day. No run of either workflow appears after 2026-09-26, although `origin/main` has commits up to 2026-10-05. The cause is unverified: Actions minutes may be exhausted or Actions disabled (ASSUMED). On GitHub Free a daily 64-min soak alone is 30 × 64 = 1,920 of the 2,000 private-repo minutes a month (VERIFIED arithmetic). The harness already has `dev integrate --local-ci` for when "Actions cannot run" (`devkit/config.py:32`).

### F7. GitHub Actions specifics for small free-tier projects
- **Minutes and runners (SOURCED).** Public repos on standard GitHub-hosted runners are free. A private repo on GitHub Free gets 2,000 min a month, 500 MB of artifacts and 10 GB of cache, reset each billing cycle ([Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)). Billable minutes for private-repo jobs "are rounded up to the next minute", per job ([View job execution time](https://docs.github.com/en/actions/how-tos/monitor-workflows/view-job-execution-time)). Standard Linux runners have 4 CPU and 16 GB in public repos but 2 CPU and 8 GB in private ones ([GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)). A job may run up to 6 h. GitHub Free allows 20 concurrent jobs ([Actions limits](https://docs.github.com/en/actions/reference/limits)).
- **Budget (VERIFIED, `scripts/ci_minutes_budget.py`).** Because rounding is per job, many tiny jobs cost more than one combined job. repo-E's PR run (two jobs of about 0.2 and 0.5 min) bills 2 min, so 1,000 runs a month. One 10-min job allows 200 runs a month, about 6.7 a day. A 10-min job plus 3 small jobs bills 13 min, so 153 runs a month. For private repos: fold small checks into one job, and keep heavy nightly work off Actions or within budget.
- **Measured CI wall times (VERIFIED, `scripts/ci_job_durations.py`, last 15 successful PR and push runs).**

  | Repo / workflow | Job | Median | Max |
  |---|---|---|---|
  | agent-harness `ci` | `check` | 1.3 min | 1.5 min |
  | agent-harness `ci` | `template` | 0.3 min | |
  | agent-harness `ci` | `plugin` | 0.2 min | |
  | repo-E `gate` | `check` | 0.2 min | |
  | repo-E `gate` | `citations` | 0.5 min | |

  Both repos are far inside the 10-min budget. Only repo-L (F6) is not.
- **Pitfalls (SOURCED).**
  - A required workflow skipped by `paths` or branch filters leaves its checks "Pending" and blocks merging. A job skipped by an `if:` reports Success ([Troubleshooting required status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks)). Use job-level `if:` rather than workflow `paths:` filters on required checks.
  - Scheduled workflows can be delayed under load, run at most every 5 min, and in a public repo are disabled after 60 days without repository activity ([Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)).
  - Cache entries unused for 7 days are evicted. A PR can restore caches from its base or default branch ([Dependency caching](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)). A `.testmondata` saved on main could therefore seed PR selection, but a 7-day-idle repo loses it (BELIEVED).
  - `concurrency` with `cancel-in-progress: true` cancels superseded runs ([Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)). The harness already scopes cancellation to PRs only (`.github/workflows/ci.yml`).
- **Parallelism tools (SOURCED via API).** [pytest-xdist](https://github.com/pytest-dev/pytest-xdist): MIT, 1,919 stars, active. [pytest-split](https://github.com/jerry-git/pytest-split): MIT, 0.11.0, splits by recorded durations across CI jobs. In a private repo, splitting adds per-job rounding (above), so it pays off only once one job passes about 10 min (BELIEVED).

### F8. Does CI help at all? Population studies
- **ASE 2016 (SOURCED).** A study of 34,544 GitHub projects, 1,529,291 builds and 442 surveyed developers. It reports evidence "that CI helps projects release more often" ([Usage, costs, and benefits of continuous integration in open-source projects](https://doi.org/10.1145/2970276.2970358) (ASE 2016)).
- **FSE 2015 (SOURCED, abstract truncated).** In historical GitHub data, the main finding is that CI improves project productivity ([Quality and productivity outcomes relating to continuous integration in GitHub](https://doi.org/10.1145/2786805.2786850) (FSE 2015)). The quality half of the claim was cut off in the abstract I fetched, so it is unverified.
- **An EMSE 2019 study on long CI build durations (EMSE 2019, [An empirical study of the long duration of continuous integration builds](https://doi.org/10.1007/s10664-019-09695-9) (EMSE 2019)).** No abstract came back, so it is not used.

## Proposed size-tiered defaults for #114 (BELIEVED, built on F1-F7)

| Size | Per change (gate) | Before merge | Scheduled |
|---|---|---|---|
| Small (<~1k tests, gate <2 min) | Full non-slow suite, random order, xdist | `dev integrate` re-gates the merged tree | Weekly `--full` plus live tests |
| Medium (gate 2-10 min) | Full suite. `--affected` or testmon locally only. Fold jobs into one in private repos | Same | Nightly `--full`, mutation sample on changed modules |
| Large (gate >10 min) | Selected tests (testmon or dependency-based) plus a fixed smoke set. The full suite moves to before-merge | Full suite on the merged tree (serial queue, or a merge queue if org-owned) | Nightly full, slow, live and soak. Flaky quarantine report |

Two trip-wires apply at every size. First, gate wall time above about 10 min is a signal to tier (DORA, Fowler). Second, a quarantine count above a ratchet means fix the tests before adding more.

## Gaps not closed
1. **DORA 2024's AI effect sizes come only from InfoQ.** The report PDF was not read.
2. **Current GitHub merge-queue eligibility.** The source is the 2023 changelog. The current docs page I fetched is silent on it.
3. **How unsafe `--affected` is here.** No measurement yet of how often it misses a failing test that the full suite catches. That would take a mutation or historical-replay experiment comparing it with pytest-testmon on this repo.
4. **Why repo-L's Actions stopped after 2026-09-26.** Billing is guessed, not checked: the billing API needs the `user` scope.
5. **No controlled evidence on nightly versus per-PR defect escape,** and no Python-specific RTS study beyond the three-project SANER paper.
6. **Not read: the EMSE 2019 study (long CI builds) and Humble and Farley's commit-stage guidance.**
7. **`gh api .../timing` returned `billable.total_ms = 0` for a repo-E run.** Whether included minutes were being consumed could not be confirmed from the API.
