## Findings

### F1. No test shape has outcome data behind it. All of them are practitioner opinion.
- **Pyramid (Cohn).** Popularised in Cohn's *Succeeding with Agile* (2009), first drawn in 2003-4. The argument is that UI-level tests are "brittle, expensive to write, and time consuming to run" and prone to non-determinism. It recommends many more unit tests than broad-stack tests, with a service-level ("subcutaneous") layer between them. No data is cited. SOURCED: [Fowler, TestPyramid, 2012](https://martinfowler.com/bliki/TestPyramid.html).
- **Trophy (Dodds).** Four layers, bottom to top: static, unit, integration, end to end. The layers are framed as "return on investment", where the return is confidence and the investment is time, and the shape follows Rauch's "Write tests. Not too many. Mostly integration." The page cites no data and says testing classifications are not scientific knowledge. SOURCED: [Dodds, 2021](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications).
- **Honeycomb (Spotify).** "focus on Integration Tests, have a few Implementation Detail Tests and even fewer Integrated Tests (ideally none)". It argues that for microservices the pyramid "can be actively harmful", because many unit tests on small services couple the tests to the code. It gives no numbers beyond "milliseconds to a few seconds" of run-time cost. SOURCED: [Schaffer, Spotify Engineering, 2018](https://engineering.atspotify.com/2018/01/testing-of-microservices).
- **Fowler's reconciliation.** The pyramid-versus-honeycomb/trophy debate is "moot" because the camps define "unit test" differently. The honeycomb's "integration test" is roughly his *sociable* unit test. Debating percentages is "a distraction" next to tests that are expressive, have clear boundaries, and run quickly and reliably. No data is cited. SOURCED: [Fowler, On the Diverse And Fantastical Shapes of Testing, 2021](https://martinfowler.com/articles/2021-test-shapes.html).
- **The only shape-compliance study found** examined 5 agile projects' counts of unit, integration and UI tests against the pyramid. It concludes that practitioners should apply "more critical thinking" to the models in the literature and that alternative models are needed. It measures shape, not defects. SOURCED (abstract only): [Test automation pyramid from theory to practice](https://doi.org/10.1109/aqtr.2018.8402699), Contan et al..
- BELIEVED: the shapes are claims about **cost** (speed, flakiness, how well a failure points to its cause), not about bug-finding power. The data below supports the cost side and undercuts the "unit tests find different bugs" side.

### F2. The Google ratio is 80/15/5 in *Software Engineering at Google*. 70/20/10 is a 2015 blog's "good first guess".
- The SWE-book chapter on unit testing recommends "around 80%" narrow-scoped unit tests, "15%" medium-scoped integration tests and "5%" end-to-end tests. It names two antipatterns: the ice-cream cone, and the hourglass (many unit and E2E tests, few integration tests). SOURCED: [SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html).
- "As a good first guess, Google often suggests a 70/20/10 split … The exact mix will be different for each team". The post's evidence is a "composite sketch" of one team's E2E-heavy release, not measured data. SOURCED: [Wacker, Google Testing Blog, 2015](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html).
- So the brief's "70/20/10 (Software Engineering at Google)" attribution is wrong. Neither ratio has published data behind it (SOURCED: neither page cites any). Both are counts of test cases, not shares of run time or effort.

### F3. Google's sizes are enforceable resource limits, separate from scope, and size predicts flakiness (the one shape-adjacent claim with large-N data).
- **Size** describes the resources a test may use. Small runs in a single process, with no sleep and no I/O. Medium runs on a single machine, with network to localhost only. Large may use anything. **Scope** is a separate axis: narrow, medium or large. "Small tests, regardless of the scope, are almost always faster and more deterministic". SOURCED: [SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html).
- The 2010 table sets timeouts of 60, 300 and 900+ s. Its main argument is that size limits can be *policed* (for example with a Java security manager), and tests must run in any order. SOURCED: [Stewart, Test Sizes, 2010](https://testing.googleblog.com/2010/12/test-sizes.html).
- **Flakiness by size (one week, about 4.2M tests).** Small tests were 0.5% flaky, medium 1.6%, large 14%. Here a test is flaky if it had at least one flaky run that week. The share flaky against binary size has r² = 0.82, and against RAM r² = 0.76 (bucketed linear fit). By tool: Python WebDriver tests were 18.72% flaky and Android emulator tests 25.46%, against 1.65% across all tests. RAM and binary size explained more of the variation than the tool did. SOURCED: [Listfield, 2017](https://testing.googleblog.com/2017/04/where-do-our-flaky-tests-come-from.html). This is an internal blog analysis, not peer reviewed, and the r² values are on bucket means, which inflates them (BELIEVED).
- **Run-level rate.** About 1.5% of all test runs were flaky, almost 16% of tests had some flakiness, and about 84% of observed pass-to-fail transitions involved a flaky test. SOURCED: [Micco, 2016](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html). The later book gives about 0.15% and says that as flakiness approaches 1%, "the tests begin to lose value". SOURCED: [SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html).
- **Arithmetic (VERIFIED, inline `python3 -c` loop computing (1-p)^n in this round).** For independent tests with per-run flake rate p, P(a run of n tests has no flaky failure) = (1-p)^n. At p = 0.15%, n = 800 gives 0.30. At p = 0.5%, n = 800 gives 0.018. At p = 1.5%, n = 1000 gives effectively 0, with 15 expected flaky failures, which matches Micco's "15 tests will likely fail". Do not plug the per-size weekly shares (0.5/1.6/14%) in as p; they are per-test-per-week, not per run.

### F4. The unit/integration distinction does not separate bug-finding power. It does separate fault localisation.
- **Sociable vs solitary.** Jay Fields coined the terms. Solitary tests replace collaborators with doubles; sociable tests use the real ones. Mockists prefer solitary tests and classicists (Fowler) prefer sociable ones. For speed, the commit suite should be "fast enough that you're not discouraged from running them", with Beck's rule of thumb of 10 minutes or less. SOURCED: [Fowler, UnitTest, 2014](https://martinfowler.com/bliki/UnitTest.html).
- **Trautsch, Herbold and Grabowski (JSS 2020).** 38,782 Java test cases were classified by the IEEE definitions and assessed with mutation testing over five defect types. "We could not find any evidence that one test type is more capable of detecting certain defect types than the other one". The definitions "do not fit modern software development", and usage-based definitions are proposed. SOURCED: [doi:10.1016/j.jss.2019.110421](https://doi.org/10.1016/j.jss.2019.110421) (abstract via [the group's page](https://www.swe.informatik.uni-goettingen.de/node/2878)).
- **Trautsch dissertation (2019), 27 Java and Python projects, 49,000+ tests.** Detected defect types "do not differ", "unit tests are better able to pinpoint the source of a defect", and there are "no significant differences in their execution time". SOURCED: [abstract page](https://www.swe.informatik.uni-goettingen.de/node/2889). The faults were mutants, not real faults, and the work comes from one research group (BELIEVED caveat).
- **Python projects (ICST 2017).** Over 70K revisions of 10 Python projects, developers "believe that they are developing more unit tests than they actually do", most projects have "a very small amount of unit tests", and the unit-test definition used changes the result. SOURCED: [Are There Any Unit Tests? An Empirical Study on Unit Testing in Open Source Python Projects](https://doi.org/10.1109/icst.2017.26), Trautsch and Grabowski.
- BELIEVED implication: a reviewer that classifies tests should not label them "unit" or "integration" by directory or name. It should use measurable traits: the size limits from F3, run time, mocks or doubles in use, and whether the test touches I/O, network or subprocesses.

### F5. Test Desiderata (Beck) is a design vocabulary with explicit trade-offs, not an evidence base.
- There are 12 properties: isolated, composable, deterministic, fast, writable, readable, behavioral, structure-insensitive, automated, specific, predictive, inspiring. Some support each other, and some interfere (more predictive means slower). No data is cited. SOURCED: [testdesiderata.com](https://testdesiderata.com/).
- BELIEVED: this is the most useful rubric for an LLM test reviewer. Each property maps to a checkable signal: deterministic maps to reruns, fast to durations, isolated to random-order runs, behavioral to mutants, and structure-insensitive to churn of tests with no behaviour change.

### F6. Mutation testing has the strongest effectiveness evidence of any adequacy measure, and Google shows how to run it per change.
- **Mutants against real faults (FSE 2014).** 357 real faults in 5 Java programs (321K LOC) and 230K mutants. 73% of real faults are coupled to mutants from common operators, and 17% (mostly algorithmic changes or code deletion) are coupled to none. Mutant detection correlates with real-fault detection independently of coverage, and more strongly than statement coverage does. SOURCED: [Are mutants a valid substitute for real faults in software testing?](https://doi.org/10.1145/2635868.2635929), Just et al. (author PDF).
- **Contrary evidence (ICSE 2018).** On CoreBench and Defects4J, "all correlations between mutation scores and real fault detection are weak when controlling for test suite size". Even so, suites ranked top by mutation score detect significantly more faults than random suites of the same size. Mutants are "good guidance" for improving a suite but a weak predictor of its fault detection. SOURCED: [Are mutation scores correlated with real fault detection?](https://doi.org/10.1145/3180155.3180183), Papadakis et al..
- **Google, State of Mutation Testing (ICSE-SEIP 2018).** Diff-based, probabilistic mutation that skips uncovered and "arid" lines. 6,000 engineers use it in code review, and it processes about 30% of diffs that have coverage. SOURCED: [State of mutation testing at google](https://doi.org/10.1145/3183519.3183521), Petrović and Ivanković.
- **Google, Practical Mutation Testing at Scale (TSE 2021).** Mutation is incremental (only changed code, at review time), with arid-node suppression, one mutant per line, and at most 7 × (files in the changelist) surfaced. The median number of mutants per changelist is 820 traditionally, 77 at one per line, and 7 at one per line after arid suppression. Developers first rated 85% of surfaced mutants unproductive; after suppression rules, 82% of surfaced mutants with feedback were rated productive. 87.5% of generated mutants were killed by the existing tests. The evaluation covered more than 24,000 developers on more than 1,000 projects. SOURCED: [Practical Mutation Testing at Scale: A view from Google](https://doi.org/10.1109/tse.2021.3107634), Petrović et al. (text read from [arXiv:2102.11378](https://arxiv.org/abs/2102.11378)). The abstracts disagree on scale: the TSE abstract gives 150M tests a day and the arXiv abstract 500M.
- **Does mutation testing improve practice? (ICSE 2021).** Almost 15M mutants over six years. Exposed developers write more test hunks, and submitted changelists have significantly fewer live mutants than at review start. Coverage change correlates weakly negatively with exposure (rs = −0.17), so the extra tests target mutants, not coverage. Of 1,502 high-priority bugs whose bug-introducing change was already covered by tests, 70% were coupled to a mutant that would have been reported on that change. In more than 90% of lines, all mutants share one fate, so one mutant per line is enough. The study is observational: projects opted in, so selection is not ruled out (BELIEVED). SOURCED: [Does Mutation Testing Improve Testing Practices?](https://doi.org/10.1109/icse43902.2021.00087), Petrović et al. (text from [arXiv:2103.07189](https://arxiv.org/abs/2103.07189)).
- BELIEVED implication for #114: run mutation on the **diff only**, sample one mutant per changed line, skip arid lines (logging, asserts, constants), cap what is surfaced, and report it, not gate on it. Use a mutation score as an occasional audit signal, never a ratchet, given Papadakis 2018.

### F7. Property-based tests: strong per-test mutation evidence in Python, limited by how hard they are to write.
- **Ravi and Coblenz (OOPSLA 2025, PACMPL).** Corpus of 426 Python programs that use Hypothesis, with mutation testing on 40 projects. On average, each property-based test finds about 50 times as many mutations as the average unit test. Tests that check for exceptions, collection inclusion or types are more than 19 times as effective as other PBT kinds. 76% of the mutations found were found within the first 20 inputs. SOURCED: [doi:10.1145/3764068](https://doi.org/10.1145/3764068). This is per test, not per line of test code or per second; one PBT runs up to 100 examples by default (BELIEVED caveat; default SOURCED: [Hypothesis API](https://hypothesis.readthedocs.io/en/latest/reference/api.html)).
- **Goldstein et al. (ICSE 2024).** 30 interviews at Jane Street. PBT is used mainly on components of complex systems, where it is expected to give more confidence than example-based unit tests "yet still run quickly as part of their normal test suite". Differential or model-based properties were "by far the most widely implemented", and round-trip properties are popular. SOURCED: [doi:10.1145/3597503.3639581](https://doi.org/10.1145/3597503.3639581) (author PDF).
- **Oliveira et al. (EMSE 2026).** 367 PBTs from 244 Python projects; the median PBT is 14 LOC. The main difficulty is data-generation strategies (36.62% of 213 Stack Overflow posts). Hypothesis's Ghostwriter fully automated only 18.23% of 203 tests. SOURCED: [doi:10.1007/s10664-026-10953-w](https://doi.org/10.1007/s10664-026-10953-w).
- **Tool (checked 2026-10-12).** Hypothesis 6.169.0, MPL-2.0 on PyPI, 9,077 stars, pushed 2026-10-11, not archived. On CI it defaults to `derandomize=True`, and failing examples are stored in `.hypothesis/examples`. SOURCED: [Hypothesis API](https://hypothesis.readthedocs.io/en/latest/reference/api.html). This is the best free option for Python.

### F8. Contract tests: well-defined practice with little outcome data.
- **Fowler (2011).** Contract tests check that your test doubles behave like the real external service. They "need not be run as part of your regular deployment pipeline" (daily is often enough), and a failure should "trigger a task" rather than break the build. SOURCED: [Fowler, ContractTest](https://martinfowler.com/bliki/ContractTest.html).
- **Pact.** Contract testing checks "an integration point by checking each application in isolation". It is consumer-driven, so provider behaviour that no consumer uses can change freely. Provider-only checks against an OpenAPI spec give no assurance that consumers call the provider correctly. SOURCED: [Pact docs](https://docs.pact.io/).
- **Evidence.** Only qualitative studies were found. Ayas et al. mined 16 microservice repositories, studied 4 that use consumer-driven contracts in depth, and report "no empirical evidence on the overall testing architecture". SOURCED: [doi:10.1109/seaa56994.2022.00022](https://doi.org/10.1109/seaa56994.2022.00022). Lehvä et al. 2019 is a single case study; only its metadata was fetched, so it carries no claim here.
- **Tools (checked 2026-10-12).** pact-python 3.4.1, MIT, 685 stars, pushed 2026-10-13. schemathesis 4.31.0, MIT, 3,663 stars, pushed 2026-10-12. Neither is archived.
- BELIEVED application to an agent harness: the "contracts" are its CLI and JSON output formats, the copier template, and the hook protocol consumed by sibling repositories. Snapshot or schema tests on those outputs are the cheap analogue of consumer-driven contracts. A full Pact broker is overkill for one owner.

### F9. Data versus opinion summary

| Claim | Status |
|---|---|
| Any shape (pyramid, trophy or honeycomb) yields fewer escaped defects | Opinion; no outcome study found |
| 70/20/10 or 80/15/5 ratios | Opinion (Google rules of thumb, no data published) |
| Larger or more resource-hungry tests are flakier | Data (Google, 4.2M tests, blog not peer reviewed) |
| Unit and integration tests catch different defect types | Contradicted (Trautsch 2020, mutants) |
| Unit tests localise faults better | Data (Trautsch 2019 dissertation) |
| Coverage as a target | Weak (see existing note) |
| Mutants couple to real faults; mutation guidance makes better tests | Data (Just 2014; Google 2021); correlation weak once size is controlled (Papadakis 2018) |
| PBT finds more mutants per test | Data (Ravi and Coblenz 2025, one study, mutants) |
| Contract tests reduce integration failures | No quantitative data found |
| Test Desiderata properties | Vocabulary, not evidence |

## Gaps seen, not closed
- No controlled or observational study links suite **shape** (unit:integration:E2E ratio) to escaped defects or lead time. Worth one more targeted search, for example MSR datasets of test-type ratios against post-release bugs.
- Whether mutmut 3.x (BSD-3-Clause, 1,476 stars, pushed 2026-09-12) or cosmic-ray (MIT, 660 stars, pushed 2026-08-09) can mutate **only changed lines** with one mutant per line, as Google does. Not checked; needed for #114.
- Luo et al. FSE 2014 ([doi:10.1145/2635868.2635920](https://doi.org/10.1145/2635868.2635920)) and other flaky-root-cause taxonomies were found but not read. They belong to the flaky-tests round.
- The Ravi and Coblenz "50×" figure is not normalised by run time or test LOC. Its full text was not read, so it is unknown whether the paper reports a per-second or per-LOC comparison.
- Lehvä et al. 2019 contract-test case study: abstract unavailable through the search sources.
