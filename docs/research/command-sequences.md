## 0. Findings in one paragraph
In the harness-run transcripts (repo-E and H, 2026-10-11..20, a 10-day window: 723 transcripts, 40,297 turns, 31,650 Bash calls, about $2,252 modelled), **mechanical multi-step sequences are rare and cheap; the recurring cost is exploration.** The most frequent sequence for builders, researchers and reviewers is `grep -n` then a `sed -n` window of the same file (1,800 pairs, a turn cost of $50 or 2.2 % of spend), but each window is a decision on what grep printed; a one-call `grep -C` alternative would save at most about $5 in the window, and in our model it costs more than the turn it saves in 74 % of the pairs we could check. The mechanical sequences the brief names are real (the 2026-10-19 lead session: 18 integrates with a hand-written checks wait, 13 worktree-add-plus-claim commands), but agents already chain them into one Bash call (84 % and 88 %), so a dev subcommand saves command text and error paths, not turns: about 40 lead turns ($3) for integrate, under $1 for dispatch prep. The premise of "python3 -c json filters over gh output" does not hold: 85 % of `gh --json` calls already use `--jq`, and 691 of the 820 Bash calls with a JSON filter read `curl` output, mostly researchers calling the GitHub, literature and registry APIs directly. Three cheap changes are worth filing because each removes a prescribed manual step or a recurring failure, not for tokens: **integrate waits for pending checks** (#322: 43 % of integrate calls carry a manual wait, 15 refusals), **`dev board brief` prints the `board new` form** (#324: `board new --help` in 151 of 723 transcripts), and **researchers check GitHub repositories with authenticated `gh api --jq`** (#323: 222 curl-into-python calls, 7.7 % failing). Everything else is rejected with a reason in §3.4. Together the three save about $9, 0.4 % of the window's spend, against up to 11.9 % fewer LLM calls reported for meta-tools on benchmarks where each tool call is a separate model step.

## 1. Question, data and method
The question (#321): which recurring multi-step command sequences, run by the lead and by workers, should a dev subcommand, a flag or a script replace, ranked by frequency, tokens and error rate, with a spec and an estimated saving for each, and without proposing what `uv run dev --help` or the v0.1.10 [CHANGELOG](../../CHANGELOG.md) already provide?

**Data (VERIFIED, [sequences.py](_scratch/command-sequences/sequences.py); outputs [report-harness.json](_scratch/command-sequences/report-harness.json) for repo-E and H and [report.json](_scratch/command-sequences/report.json) for all three projects; arithmetic in [savings.py](_scratch/command-sequences/savings.py)).**
- **Harness-run:** repo-E (721 transcripts) and H, this repository (2 main sessions; most H work runs from repo-E sessions and is counted there), 2026-10-11..20. Every number below is for these two unless marked otherwise. Main sessions are the lead; subagents take their role from `.meta.json` (builder, researcher, reviewer = reviewer + security-reviewer + research-auditor, tester, other). 47,761 tool calls. Modelled spend $2,252. It is of the same order as the $2,356 modelled for repo-E's first week in [harness-efficiency.md](harness-efficiency.md) §2 (this model leaves out visible output): a sanity check of the cost model, not a replication.
- **Non-harness baseline:** L1 (406 transcripts, 2026-09-25..10-12, $3,819 modelled) ran no `dev` command at all, so it is not harness-run. It is kept only as a baseline: the same exploration loop dominates there (2,434 grep-then-window pairs) and its builders ran `pytest` directly 3,338 times.

**Method.**
- Each Bash command is split into steps at unquoted `&&`, `||`, `;`, `|` and newlines (heredoc bodies dropped), and each step is normalised to a label: command plus subcommand words, no arguments (`dev board claim`, `gh pr checks`, `git worktree add`, `python -c json<stdin`). Only public command names reach the report; anything else becomes `other` or `script`.
- Sequences are counted three ways: pipes inside one call (the step that consumes an output), n-grams (2-4) of consecutive tool calls with at least two Bash calls, and detectors for the sequences the brief names (sections A-K of `detectors`). The unit is an occurrence of the sequence; detector A (JSON filters) counts each Bash call once.
- Cost per occurrence: each turn re-reads its context at the cache-read price and writes the command plus 233 hidden output tokens; each output is written to the cache once and re-read on every later turn until the next compaction. Opus 5.5 list prices, 4 characters per token of tool output and 0.443 tokens per character of model text, all as in [harness-efficiency.md](harness-efficiency.md) §2. The mean modelled cost of the turn that issues a Bash call: lead $0.077, builder $0.034, researcher $0.038, reviewer $0.018 (VERIFIED).
- Rank score: modelled $ x (1 + error rate). A saving counts the turns a replacement removes at that role's turn cost, plus intermediate output no longer carried; it ignores wall-clock time.

**Limits.**
- Pipes mask exit codes, so error rates of piped commands are lower bounds.
- Outputs are kept as their first and last 400 characters. So `grep_hits` sees only the hits in grep's first 400 characters, while 1,507 of the 1,800 grep outputs in §3.4 are longer than 800 characters: the 583 pairs whose window "holds a hit" are a lower bound.
- The one-call `grep -C` alternative is priced as one window, the size the agent chose, per hit. Real `-C` merges overlapping windows and may need smaller ones. Both limits bias the comparison against `-C`, so §3.4 leads with its maximum saving, which does not depend on them.
- v0.1.10 shipped on 2026-10-19, so one lead session (2026-10-19..20) runs on it.

The lead's top n-grams are `gh pr comment > SendMessage > gh pr comment` (n = 10) and `grep > sed -n` (n = 18). Pipes say the same: `grep | head` is the most common pipe in every role (researcher n = 3,532, builder n = 2,364).

## 3. Candidates: spec, saving, and what exists
### 3.1 `dev integrate` waits for checks still running on the PR head (#322, P2)
- **Exists?** integrate already waits for every check on a head it pushed (`await_checks`, bounded by `checks_wait_s`, 900 s by default), but on the PR's own head it counts a pending check as unfinished feedback and refuses (VERIFIED by reading `_integrate` and `unfinished` in `devkit/workflow.py`). Step 3 of the lead skill tells the lead to "wait for green checks" first.
- **Spec.** Input: the PR number, as today. When the only unfinished items are pending checks, wait for them with `await_checks`, read feedback again, then continue. A failing check, requested change or unresolved thread still refuses at once; a timeout ends in the existing `waiting` result, which a rerun resumes. Output unchanged: the lead branches on the last `RESULT-JSON` line.
- **Saving (VERIFIED, savings.py).** 25 lead turns spent reading checks in a separate call and 15 reruns after a pending-check refusal: 40 lead turns, $3.09 over the window (0.14 % of spend), 15 of the 39 refusals, and the hand-written `gh pr checks <n> --watch --interval 20 >/dev/null 2>&1;` in 133 commands. Worth building because it reuses code that exists and removes a prescribed manual step (BELIEVED), not for tokens.
- **Not proposed:** a quieter integrate. The lead pipes 364 of 365 integrate calls, but what it keeps is about 400 characters, r2-against warns that cutting output can raise cost, and the `RESULT-JSON` contract already serves the next step.

### 3.2 `dev board brief` prints the `board new` form (#324, P3)
- **Exists?** The brief's Commands section lists claim, navigate, test, check, pr and beat, but not `board new` (VERIFIED, `devkit/board.py`), which workers need for out-of-scope findings.
- **Spec.** One line: `uv run dev board new --type <type> --title "..." --done "..." --owns <path> --refs <n>`. No new command.
- **Saving (VERIFIED).** 154 `board new --help` calls in 151 of 723 transcripts (21 %), $5.24 of turns; 256 help-then-use pairs across all dev commands. Small in money; it removes a lookup that most follow-up-filing runs make (BELIEVED).

### 3.3 Researchers check GitHub repositories with authenticated `gh api --jq` (#323, P3)
- **Exists?** `dev reuse check` verifies registry packages (PyPI, npm, cargo) only (VERIFIED, `check` in `devkit/reuse.py`). researcher.md tells researchers to check every other tool "through the API (`https://api.github.com/repos/<o>/<r>`…)", which they do with unauthenticated `curl` piped into a hand-written Python filter.
- **Spec.** A text change: `gh api repos/<o>/<r> --jq '{stars: .stargazers_count, pushed_at, archived, license: .license.spdx_id}'`. `gh` is authenticated, and guard_bash allows read-only `gh api` for every role (VERIFIED, `plugins/harness-ops/scripts/guard_bash.py`).
- **Saving (VERIFIED, counted once per Bash call).** 222 calls (203 by researchers, about 74 per 100 researcher runs), 17 failed (7.7 %), $0.65 of failed turns. 13 of the 243 Bash calls that curl the GitHub API printed a rate-limit message or a 403 (detector A in sequences.py). The unauthenticated limit is 60 requests per hour against 5,000 for an authenticated user (SOURCED, [GitHub REST API rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)). A `dev reuse check owner/repo` mode would also apply gates G1-G6, but the one-line text change is the simplest arm and goes first (BELIEVED).

### 3.4 Not worth building, with the reason
- **`grep -n` then `sed -n` windows** (the largest by volume). The robust number: in the pairs where a one-call `grep -C` would come out ahead, it saves at most about $5 over the window (149 pairs; VERIFIED, `C one-call grep -C instead`). Of the 583 pairs whose window holds a parsed hit, our model has `-C` losing in 434 (74 %; repo-E alone 433 of 581, 75 %), but that share leans on the two biased assumptions in §1. The deciding argument is structural: the window is a decision on grep's output, so a fixed command cannot make it. `dev code find` and `dev code show` exist and are 3-6 % of navigation ([harness-efficiency.md](harness-efficiency.md) §5). How agents navigate is an interface question: SWE-agent showed that a purpose-built agent-computer interface "significantly enhances an agent's ability to … navigate entire repositories" (SOURCED, Yang et al., NeurIPS 2024 ([arXiv 2405.15793](https://arxiv.org/abs/2405.15793)), abstract). That is a different study from bundling a fixed sequence.
- **`dev code outline` then `sed -n`.** No turn to save: the outline already ends with the `dev code show` or `sed -n` hint, and choosing the window needs the outline (VERIFIED, 295 of 469 outlines).
- **Dispatch prep (`git fetch` + `git worktree add` + `dev board claim`).** 77 of 88 are already one compound call; a `claim --worktree` flag would save about 10 turns ($0.85 at the lead's turn cost) and some command text (VERIFIED).
- **JSON filters over `gh` output.** 85 % of `gh --json` calls already use `--jq`; 27 Bash calls fed `gh` output into a JSON filter (VERIFIED). The curl filters on the literature APIs (220) are now denied by guard_bash (#227, v0.1.10), and `dev lit get` takes several ids at once.
- **PR and issue body edit loops.** 107 runs of 2.69 calls with 7.5 % errors, about $6 of turns (VERIFIED); a `--replace OLD NEW` body edit would save little. Re-measure after v0.1.10, whose session-link refusal in `dev pr` and `integrate` may make these loops more frequent.
- **Persisted outputs read back.** 323 of the 411 read-backs use Read, which the v0.1.10 read guard now windows (#265); the Bash read-backs are about 90 (VERIFIED).
- **Polling and `sleep`.** 265 bare sleeps fail 23.4 % of the time, but all polling cost $18 for all agents in repo-E's first week ([harness-efficiency.md](harness-efficiency.md) §2), and the fix is Claude Code's background notification, not a dev command.
- **Trimming `dev check` or `cite-check` output that agents pipe into `tail`.** Rejected in [r2-against](_scratch/harness-efficiency/r2-against.md) §3: their output is already a summary. The refusals of `dev pr` behind a pipe were fixed in v0.1.10 (#261).

## 4. Why the savings are this small
- **Agents already chain deterministic steps.** In Claude Code a Bash call takes a whole shell program, so the agent chains mechanical steps itself (84-88 % of the lead's mechanical sequences, and every JSON filter, run in one call; VERIFIED §2). A dev subcommand then removes command text and error paths, not turns. Meta-tools save most where each tool call is a separate model step: Agent Workflow Optimization turns recurring tool-call sequences into "deterministic, composite tools" and "reduces the number of LLM calls up to 11.9% while also increasing the task success rate by up to 4.2 percent points" on two benchmarks (SOURCED, Abuzakuk et al. 2026 ([arXiv 2601.22037](https://arxiv.org/abs/2601.22037)), abstract). Workflows induced from past runs and given to the agent raised relative success 24.6 % and 51.1 % on Mind2Web and WebArena, with fewer steps on WebArena (SOURCED, Wang et al., ICML 2024 ([arXiv 2409.07429](https://arxiv.org/abs/2409.07429)), abstract). Neither measures shell-based coding agents, and here most of the bundling has already happened (BELIEVED).
- **The harness already replaced the costly ones.** `dev pr`, `dev integrate` (re-gate, merge, close issues, retarget), `dev board brief` (issue, feedback, commands) and `dev board claim` each stand for several steps; what remains is the glue around them.
- **The remaining cost is reading.** The grep/sed loop is how agents read code ([harness-efficiency.md](harness-efficiency.md) §5: 28,911 Bash reads against 1,301 Read), in harness-run and non-harness repositories alike. Changing it is a question about the navigation interface (§3.4, SWE-agent), not about command sequences.

## 5. Recommendation for this project
- Build #322 (P2), then #324 and #323 (P3). Together they remove about 40 lead turns, 154 help lookups and 17 failed API calls per 10-day harness window: about $9, 0.4 % of the window's $2,252 modelled spend (VERIFIED arithmetic, savings.py). Judge each on its DONE WHEN (manual waits under 10 % of integrate calls, `board new --help` in under 3 % of transcripts, GitHub curls under 10 per 100 researcher runs), not on spend, which these changes cannot move measurably.
- Build no command for the grep/sed exploration loop, dispatch prep, gh JSON filters or body edits (§3.4). Re-run `sequences.py` after two weeks on v0.1.10; if body-edit loops pass 150 per 10 days, or a new sequence above $10 per 10 days appears whose steps do not depend on the previous output, file it then.
- Reuse this script for later harness versions rather than writing a new one: `python3 sequences.py extract --cache <a path outside the repo> repo-E=<dir> L1=<dir> H=<dir>`, then `python3 sequences.py report --cache <same path> --projects repo-E,H > report-harness.json` (and without `--projects` for `report.json`), then `python3 savings.py report-harness.json report.json`.
